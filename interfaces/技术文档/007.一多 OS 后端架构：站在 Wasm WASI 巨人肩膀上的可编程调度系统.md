# 一多 OS 后端架构：站在 Wasm/WASI 巨人肩膀上的可编程调度系统

## 概述

一多 OS 的 WIT 接口是**标准接口定义**，但实际功能需要通过**后端适配器（Backend Adapter）**来对接现有的成熟库。

---

## 核心概念澄清：UniHAL vs 完整体系

| 名称 | 范围 | 说明 |
|------|------|------|
| **UniHAL** | 后端适配器层 | 技术术语，类比 Android HAL，但更先进（可编程调度） |
| **完整一多 OS 体系** | 四层 + 四元架构 | 包括细胞组合配置、调度整合、计算细胞、后端适配器等全部内容 |

**重要说明：**
- **UniHAL** = 后端适配器（本文档描述的主要内容）
- **UniHAL ≠ 一多 OS 全部** - 它只是整个体系的一层，还有更丰富的上层能力

## UniHAL（后端适配器）的核心理念

**后端适配器不只是简单的适配器，而是一个可编程的调度系统！**

这是我们与传统 HAL 最大的区别：
- 传统 HAL：只是接口翻译，没有智能
- UniHAL：支持策略配置、动态选择、自动降级、健康检查

## 一多 OS 与 Wasm/WASI 的完美分工

一多 OS 的定位是**智能调度与整合专家**，与 Wasm/WASI 生态形成完美互补：

### 基础设施层：Wasm/WASI 生态复用
一多 OS 直接采用 Wasm/WASI 生态提供的成熟基础设施：
- **运行时安全隔离**：基于 WebAssembly 的沙箱机制
- **跨平台系统调用**：通过 WASI 标准接口访问文件、网络、时钟等系统资源
- **组件化架构**：采用 Wasm Component Model 实现功能模块的隔离与组合
- **内存管理**：使用 WebAssembly 的线性内存模型

### 核心价值层：一多 OS 的创新领域
一多 OS 专注于提供差异化的核心能力：
- **领域标准接口定义**：通过 WIT 定义 `yiduo:hw-camera`、`yiduo:ai-inference` 等行业级标准接口
- **可编程调度与策略引擎**：实现计算资源（如 AI 模型在 CPU/GPU/NPU 间）的智能调度与后端实现的动态适配
- **声明式配置与动态组装**：通过 YAML 配置文件实现组件的声明式组合与部署
- **健康监测与容错机制**：提供系统运行时监控、自动降级与恢复能力

### 架构优势
这种分层设计具有显著优势：
- **关注点分离**：一多 OS 专注于调度与整合，底层基础设施复用成熟生态
- **生态协同**：与 Wasm/WASI 形成互补，避免重复实现
- **向前兼容**：当 WASI 标准演进时，上层 WIT 定义与调度逻辑保持稳定，仅需调整适配器层即可无缝对接

## 可编程调度系统的特性

### 1. 动态选择
- 根据硬件、场景、性能自动选择最佳后端
- 例如：摄像头设备 → 优先选择 libcamera，没有则降级为 OpenCV

### 2. 策略配置
- 可配置的调度策略
- 例如：优先性能 / 优先兼容性 / 优先兼容性

### 3. 降级方案
- 主要后端不可用时，自动降级到备选后端
- 例如：硬件加速失败 → 回退到软件实现

### 4. 可观测性
- 可以查看当前使用的后端
- 可以监控性能指标
- 可以调试和优化

## 细胞组合配置：应用场景层

### 什么是细胞组合配置？

细胞组合配置是一多 OS 的核心创新，它允许用户根据特定应用场景，**像搭积木一样自由组合多个计算细胞**，构建完全定制化的操作系统。

每个应用场景对应一个配置文件，定义了：
- 需要加载哪些计算细胞
- 每个细胞使用哪个后端实现
- 细胞之间的协作关系

### 配置文件格式：应用场景 YAML

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: AppScenario
metadata:
  name: music-producer-station
  description: "专业音乐制作人工作站"
  category: "creative"

spec:
  # 细胞组合清单 - 定义场景需要哪些能力
  cells:
    - name: audio-processing
      required: true
      priority: 10
      backend:
        primary: "portaudio-pro"
        fallbacks: ["alsa", "mock"]
        strategy: "prefer-low-latency"
    
    - name: low-latency-io
      required: true
      priority: 9
      backend:
        primary: "rt-linux"
        fallbacks: ["posix"]
    
    - name: custom-interface
      required: true
      priority: 8
      backend:
        primary: "wayland"
        fallbacks: ["x11"]
    
    - name: midi-control
      required: false
      priority: 7
    
    - name: audio-effect
      required: false
      priority: 6

  # 场景特定的配置
  scenario-config:
    audio-buffer-size: 64
    sample-rate: 48000
    bit-depth: 32
```

### 细胞组合配置的核心特性

#### 1. 声明式组合
- 用户只需声明"需要什么"，无需关心"如何实现"
- 系统根据配置自动加载和组装细胞

#### 2. 优先级调度
- 每个细胞都有优先级设置
- 系统根据场景特性优化资源分配

#### 3. 热切换
- 支持在运行时调整细胞组合
- 无需重启整个系统

#### 4. 场景模板库
- 提供预置的场景模板
- 用户可以基于模板快速定制

## 可编程调度系统的实现思路

### 配置驱动的调度
```yaml
device:
  name: "智能摄像头"
  capabilities:
    camera:
      # 配置后端选择策略
      backend-strategy: "prefer-native"
      # 优先级排序
      backends:
        - name: libcamera
          priority: 10
          native: true
        - name: opencv
          priority: 5
          fallback: true
        - name: mock
          priority: 1
          test-only: true
```

### 可编程的调度逻辑
```
调度流程：
1. 读取配置的策略和优先级
2. 按优先级尝试每个后端
3. 检查后端是否可用（硬件支持、库存在）
4. 选择第一个可用的后端
5. 如果所有后端都不可用，报错或降级
```

## 与"计算细胞"的关系

后端适配器是**计算细胞的内部实现**，计算细胞是对外的标准接口！

| 概念 | 角色 | 说明 |
|------|------|------|
| **计算细胞** | 能力积木的**对外接口** | 功能独立、标准接口（WIT）、安全沙箱、跨语言、动态组合 |
| **后端适配器** | 计算细胞的**内部实现** | 对接现有成熟库（libcamera、PortAudio等），不是重新发明轮子 |

## 与四元架构的完美契合

（原"三大设计原则"已升级为更完整的四元架构）

### 对应关系一览

| 四元架构 | 原设计原则 | 系统实现 | 说明 |
|---------|-----------|---------|------|
| 💭 **配置即意志** | - | 场景配置文件 | 高维意识的直接投射 |
| 🧬 **器官即DNA** | 配置即DNA | 计算细胞 + 后端适配器 | 功能实体与遗传信息 |
| 🌳 **树形即生长路径** | 树形是器官 | 架构演化 + 模块组合 | 时空生长轨迹 |
| 🩸 **链式即血液系统** | 链式是血液 | WIT 接口 + 事件总线 | 信息流通网络 |

### 1. 💭 配置即意志（系统灵魂）

配置文件不再是冰冷的参数，而是造物主的**一念之间**：

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: AppScenario
metadata:
  name: music-producer-workstation  # 意志决定场景
spec:
  cells:
    - name: audio-processing
      backend:
        primary: portaudio-pro     # 意志选择后端
        fallbacks: [alsa, mock]    # 意志设定降级策略
```

**体现：**
- 配置文件是高维意识的直接投射
- 用户只需声明"需要什么"，无需关心"如何实现"
- 修改配置就是改变系统的"意志"

---

### 2. 🧬 器官即DNA（功能实体）

计算细胞和后端适配器本身就是固化的 DNA：

```
┌─────────────────────────────────────────────────────┐
│           WIT 接口（标准定义）               │ ← 链式血液
└──────────────────────┬────────────────────────────┘
                       │
┌──────────────────────┴────────────────────────────┐
│   ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│   │ Libcam   │  │  OpenCV  │  │   Mock   │   │ ← 器官即DNA
│   │ Backend  │  │ Backend  │  │ Backend  │   │ (不同的基因表达)
│   └──────────┘  └──────────┘  └──────────┘   │
└─────────────────────────────────────────────────────┘
```

**体现：**
- 每个细胞自带完整的功能闭环（遗传信息）
- 同一个 WIT 接口可以有多个后端实现（基因表达）
- 不同的后端像不同的器官，可以灵活组合/替换

### 3. 🌳 树形即生长路径（系统演化）

树形架构描述系统在时空中的生长轨迹：

```
应用场景
   ├── 音乐制作人（分支1）
   │    ├── 音频处理
   │    └── 低延迟IO
   │
   └── 物联网开发者（分支2）
        ├── 传感器驱动
        └── 网络协议
```

**体现：**
- 业务流程像树枝一样可以分叉、生长、修剪
- 可以通过配置改变生长方向，无需重写代码
- 支持热切换和动态调整

### 4. 🩸 链式即血液系统（信息流通）

链式架构是能量与信息的流通网络：

```
┌─────────────────────────────────────────────────────┐
│      一多 OS WIT 接口（稳定、不变化）             │ ← 链式血液

```

**体现：**
- WIT 接口是稳定的"血液"层
- 无论后端怎么变，接口保持一致
- 事件总线像神经递质一样异步传递信息

## 总结

### 核心思想

**不是重新发明轮子，而是把现有轮子装到我们的车上！**

- WIT 接口 = 标准化的轮子接口
- 后端适配器 = 把轮子装到车上的零件
- 现有库 = 现成的好轮子

### 实施优先级

1. ✅ **先做 Mock 后端** - 让系统跑起来
2. ✅ **再做 Linux 桌面后端** - 验证概念
3. ✅ **然后做嵌入式后端** - 走向真正产品
4. ✅ **其他平台** - 有资源再做

### 关键优势

- 不需要从零写驱动
- 可以利用成熟生态
- 测试方便（Mock 后端）
- 可以支持多种后端，用户选择最合适的

## 借鉴 Kubernetes/Docker Compose 的成熟经验

### 为什么要借鉴 K8s/Compose？

| 方面 | K8s/Compose 理念 | 我们的应用 |
|------|-----------------|----------|
| **配置文件即编程** | 用 YAML 声明式定义"我需要什么" | 用 YAML 声明式选择后端 |
| **关注点分离** | YAML = 声明 / Controller = 执行 | 配置 = 声明 / 调度器 = 执行 |
| **可验证性** | `kubectl apply --dry-run` | `yiduo-device apply --dry-run` |
| **健康检查** | Readiness/Liveness Probes | 后端健康检查与自动修复 |
| **容错机制** | ReplicaSet、自动重启 | 后端 Fallback、降级策略 |

---

### 借鉴点 1：声明式优先的配置设计

#### K8s 风格的 YAML 配置
```yaml
apiVersion: yiduo.dev/v1alpha1
kind: DeviceSpec
metadata:
  name: smart-camera
  labels:
    device-type: camera
    vendor: sony
    model: imx327

spec:
  # 能力声明（像 K8s 的 Pod 规格）
  capabilities:
    - name: camera
      backend:
        # 主后端
        primary: libcamera
        # 降级选项（像 K8s 的 Pod 反亲和性）
        fallbacks:
          - opencv
          - mock
        # 选择策略
        strategy: prefer-native
        # 健康检查（像 K8s 的 Probes）
        healthCheck:
          enabled: true
          intervalSeconds: 10
          timeoutSeconds: 3
          failureThreshold: 3

    - name: audio
      backend:
        primary: pulseaudio
        fallbacks:
          - alsa
          - mock
        strategy: prefer-compatibility

    - name: display
      backend:
        primary: wayland
        fallbacks:
          - x11
          - mock
        strategy: prefer-performance
```

#### 核心配置字段说明
| 字段 | 说明 | 借鉴来源 |
|------|------|---------|
| `primary` | 首选后端 | K8s 首选调度节点 |
| `fallbacks` | 降级选项 | K8s 节点亲和性降级 |
| `strategy` | 选择策略 | K8s 调度策略 |
| `healthCheck` | 健康检查配置 | K8s Readiness/Liveness |

### 借鉴点 4：健康检查与容错机制

#### 后端健康检查（像 K8s Probes）
```yaml
spec:
  capabilities:
    - name: camera
      backend:
        primary: libcamera
        fallbacks: [opencv, mock]
        # 健康检查配置
        healthCheck:
          enabled: true
          # 探测间隔（秒）
          intervalSeconds: 10
          # 超时时间（秒）
          timeoutSeconds: 3
          # 连续失败多少次触发降级
          failureThreshold: 3
          # 恢复阈值
          successThreshold: 2
          # 探测命令
          probe:
            type: exec
            command: ["camera-check"]
```

#### 容错机制
```yaml
spec:
  capabilities:
    - name: camera
      backend:
        primary: libcamera
        fallbacks: [opencv, mock]
        # 容错策略
        faultTolerance:
          # 自动降级
          autoFallback: true
          # 自动恢复
          autoRecovery: true
          # 恢复等待时间（秒）
          recoveryDelaySeconds: 60
```

## 实际目录结构与文件组织

### 完整的目录布局

一多 OS 的代码组织采用**功能导向**的目录结构，而不是严格按照四层概念划分：

```
yiduo/
├── interfaces/                      # WIT 接口定义（核心）
│   ├── base/
│   ├── env/
│   └── cap/
│       ├── camera/
│       ├── audio/
│       └── ...
├── runtime/                         # 运行时引擎
│   ├── scheduler/                   # 调度逻辑（第2层）
│   ├── cell_manager/                # 细胞加载与管理（第3层）
│   ├── backend_manager/             # 后端管理（第4层）
│   └── ...
├── adapters/                        # 后端适配器实现（第4层）
│   ├── camera/
│   │   ├── mock/
│   │   ├── libcamera/
│   │   └── opencv/
│   ├── audio/
│   └── ...
├── builtin_cells/                   # 内置 Wasm 细胞实现（第3层）
│   ├── camera_cell.wasm
│   ├── audio_cell.wasm
│   └── ...
├── scenarios/                       # 用户场景配置（第1层）
│   ├── smart-camera.yaml            # 用户自定义或预设的场景
│   ├── music-producer.yaml
│   └── ...
├── configs/                         # 系统级配置（与 scenarios/ 区分）
│   ├── tech-stacks/                 # 技术栈配置（后端选择列表、默认策略）
│   ├── system/                      # 系统级默认配置
│   └── templates/                   # 场景模板（供用户参考和定制）
├── examples/                        # 示例应用
│   ├── hello/                       # 基础 Hello World
│   ├── smart-camera/                # 智能相机场景完整示例
│   ├── custom-cell/                 # 如何编写自定义细胞的示例
│   └── ...
└── docs/                            # 文档
```

### 目录职责详细说明

#### interfaces/ - 标准接口定义
- 所有细胞的 WIT 接口定义
- 是整个系统的"契约"和标准

#### runtime/ - 核心运行时引擎
- **scheduler/**: 调度逻辑、策略引擎、健康监控
- **cell_manager/**: 负责加载和管理细胞（无论是内置还是外部）
- **backend_manager/**: 管理和协调后端适配器

#### adapters/ - 后端实现
- 各种能力的后端适配器
- 每个能力有多个可选实现

#### builtin_cells/ - 内置细胞
- 预编译的 Wasm 细胞模块
- 提供开箱即用的功能
- 由 runtime/cell_manager/ 加载和管理

#### scenarios/ vs configs/ - 配置的区别

| 项目 | scenarios/ | configs/ |
|------|-----------|---------|
| **用途** | 用户场景配置 | 系统级配置和模板 |
| **内容** | 用户实际使用的场景 | 技术栈默认值、场景模板 |
| **修改者** | 终端用户 | 系统开发者/高级用户 |
| **例子** | `my-home-surveillance.yaml` | `tech-stacks/camera.yaml`, `templates/music-producer.yaml` |

#### examples/ - 示例和学习资源
- **hello/**: 最简可用示例
- **smart-camera/**: 完整场景示例
- **custom-cell/**: 如何开发自定义细胞
- 更多实用示例...

### 概念与实现的对应关系

| 概念分层 | 主要对应的目录 | 说明 |
|---------|--------------|------|
| 细胞组合配置 | `scenarios/` + `configs/templates/` | 用户场景 + 预设模板 |
| 调度整合 | `runtime/scheduler/` | 核心调度逻辑 |
| 计算细胞 | `interfaces/cap/` + `builtin_cells/` + `runtime/cell_manager/` | 接口定义 + Wasm 实现 + 管理逻辑 |
| 后端适配器 | `adapters/` | 各种后端实现 |

**重要提示**：四层概念体系是帮助理解的**逻辑模型**，不是严格的代码包划分。一个代码模块可能参与多个概念层！

### 1. 站在巨人肩膀上

- YAML 配置符合云原生时代的习惯
- 声明式思维已经被广泛接受

### 3. 可扩展性
- 这套模式已经在大规模生产环境中验证
- 可以支持复杂的调度策略和容错机制
- 可以支持多设备、分布式场景

### 4. 清晰的职责边界
- interfaces/ 定义契约，稳定不变
- adapters/ 负责实现，可以灵活替换
- scenarios/ 用户视角，简单易用
- runtime/ 核心引擎，内部实现
