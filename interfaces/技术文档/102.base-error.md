# Base Error 接口文档

## 概述

`base/error.wit` 定义了一多 OS 中统一的错误处理标准。这些错误码被所有其他接口使用，确保错误处理的一致性。

WIT 文件位置：[../base/error.wit](../base/error.wit)

---

## 核心错误类型

### Error 枚举

```wit
enum Error {
  Success,
  InvalidArg,
  IoError,
  PermissionDenied,
  NotFound,
  AlreadyExists,
  Timeout,
  OutOfMemory,
  NotSupported,
  InternalError,
}
```

**说明**：所有接口使用的标准错误枚举。

---

## 错误码详解

| 错误枚举 | 常量名 | 错误码 | 说明 | 常见场景 |
|---------|--------|-------|------|---------|
| `Success` | `ERROR_SUCCESS` | 0 | 操作成功，无错误 | 任何成功的操作 |
| `InvalidArg` | `ERROR_INVALID_ARG` | 1 | 参数无效或非法 | 传入空指针、超出范围的参数 |
| `IoError` | `ERROR_IO_ERROR` | 2 | IO 错误 | 文件读写失败、设备通信错误 |
| `PermissionDenied` | `ERROR_PERMISSION_DENIED` | 3 | 权限不足 | 试图访问无权限的资源 |
| `NotFound` | `ERROR_NOT_FOUND` | 4 | 资源未找到 | 文件不存在、设备未连接 |
| `AlreadyExists` | `ERROR_ALREADY_EXISTS` | 5 | 资源已存在 | 创建已存在的文件或资源 |
| `Timeout` | `ERROR_TIMEOUT` | 6 | 操作超时 | 设备响应超时、网络请求超时 |
| `OutOfMemory` | `ERROR_OUT_OF_MEMORY` | 7 | 内存不足 | 内存分配失败 |
| `NotSupported` | `ERROR_NOT_SUPPORTED` | 8 | 功能不支持 | 设备不支持的功能 |
| `InternalError` | `ERROR_INTERNAL_ERROR` | 9 | 内部错误 | 系统内部错误、断言失败 |

## 错误码常量定义

```wit
const ERROR_SUCCESS: u32 = 0
const ERROR_INVALID_ARG: u32 = 1
const ERROR_IO_ERROR: u32 = 2
const ERROR_PERMISSION_DENIED: u32 = 3
const ERROR_NOT_FOUND: u32 = 4
const ERROR_ALREADY_EXISTS: u32 = 5
const ERROR_TIMEOUT: u32 = 6
const ERROR_OUT_OF_MEMORY: u32 = 7
const ERROR_NOT_SUPPORTED: u32 = 8
const ERROR_INTERNAL_ERROR: u32 = 9
```

**说明**：
* 这些常量用于与其他语言或系统的错误码映射
* 在 C FFI 或底层系统接口中，可以使用这些数字错误码
* 通常应该优先使用 `Error` 枚举而不是原始数字

## 使用示例

### 错误检查模式

```
// 调用一个可能失败的函数
let result = some-function(arg)

if result.err == Error.Success {
  // 成功，使用 result.ok
  process-data(result.ok)
} else {
  // 失败，处理错误
  match result.err {
    Error.NotFound => println("资源不存在")
    Error.PermissionDenied => println("权限不足")
    Error.Timeout => println("操作超时")
    _ => println("未知错误")
  }
}
```

### 早期返回模式

```
fn complex-operation() -> result<data, Error> {
  // 步骤1
  let step1-result = step1()
  if step1-result.err != Error.Success {
    return result-with-error(step1-result.err)
  }
  
  // 步骤2
  let step2-result = step2(step1-result.ok)
  if step2-result.err != Error.Success {
    return result-with-error(step2-result.err)
  }
  
  // 所有步骤都成功
  return result-with-ok(final-data)
}
```

## 最佳实践

### 1. 始终检查返回错误
* 不要忽略任何可能失败的函数的错误返回值
* 即使你认为"肯定不会失败"，也要检查错误

### 2. 提供有意义的错误信息
* 在记录日志时，将错误码转换为可读的描述
* 例如：`E_OUT_OF_MEMORY` 而不是只打印 `7`

### 3. 合理处理错误
* `NotFound` - 可能不是错误，而是正常情况
* `PermissionDenied` - 可能需要请求用户权限
* `Timeout` - 可以重试操作
* `InternalError` - 应该记录详细日志并报告

### 4. 错误恢复
* 对于可恢复的错误（如 `Timeout`），可以设计重试机制
* 对于严重错误（如 `InternalError`），应该考虑安全关闭或重启

### 5. 自定义错误
* 如果标准错误码不够用，可以在特定接口中定义扩展错误
* 但应该尽量复用标准错误码
