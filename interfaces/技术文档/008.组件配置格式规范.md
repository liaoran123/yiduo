# 一多 OS 组件配置格式规范

## 概述

本文档定义一多 OS 组件系统的配置格式规范。

### 💡 灵感来源：Android 应用清单

这个配置系统的设计灵感来源于 **Android 的 AndroidManifest.xml**：

| Android                   | 一多 OS              | 说明              |
| ------------------------- | ------------------ | --------------- |
| **AndroidManifest.xml**   | **Component.yaml** | 组件/应用的清单文件      |
| `<application>`           | `metadata`         | 基本信息（名称、版本、描述等） |
| `<activity>`, `<service>` | `provides`         | 组件提供的能力/接口      |
| `<uses-permission>`       | `requires`         | 组件需要的依赖/能力      |
| `<uses-feature>`          | `config`           | 配置参数和功能要求       |

**核心理念**：就像 Android 应用通过清单文件声明"我是谁"、"我能做什么"、"我需要什么"，一多 OS 的组件也通过 YAML 配置文件声明一切！

## 核心设计原则

1. **自包含**：组件定义 = 接口 + 依赖 + 实现 + 策略，一个文件搞定
2. **默认优先**：组件内置默认策略，用户只需覆盖差异
3. **场景预设**：提供多种场景的预配置
4. **递归支持**：组件可以嵌套依赖，形成树形结构
5. **声明式**：使用 YAML 格式，借鉴 Kubernetes 成熟经验

## 配置格式规范

### 1. Component（组件定义）

这是最核心的配置文件，定义一个完整的组件。

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: audio-processing
  namespace: yiduo.cap
  version: "1.0.0"
  description: "音频处理组件"
  author: "Yiduo Team"
  license: "MIT"

spec:
  # 1. 提供的接口
  provides:
    - interface: yiduo:cap/audio-play
      wit-file: "../wit/audio-play.wit"
    - interface: yiduo:cap/audio-record
      wit-file: "../wit/audio-record.wit"
  
  # 2. 需要的权限（类似 Android 的 <uses-permission>）
  permissions:
    - name: audio.record
      description: "访问麦克风录音"
      required: false
    - name: audio.playback
      description: "播放音频"
      required: true
    - name: storage.read
      description: "读取文件系统"
      required: false
    - name: network.internet
      description: "访问互联网"
      required: false
  
  # 3. 需要的依赖（支持递归）
  requires:
    - name: cpu
      interface: yiduo:base/cpu
      required: true
      version: ">=1.0.0"
    - name: memory
      interface: yiduo:base/memory
      required: true
    - name: optional-feature
      interface: yiduo:cap/optional
      required: false
    - name: camera
      interface: yiduo:cap/camera
      required: false  # ✅ 摄像头是可选的，不是所有系统都需要
      description: "仅在需要摄像功能的场景中使用"
  
  # 3. 配置参数 Schema
  config:
    $schema: "http://json-schema.org/draft-07/schema#"
    type: object
    properties:
      sample-rate:
        type: integer
        enum: [44100, 48000, 96000]
        default: 48000
      buffer-size:
        type: integer
        default: 1024
        minimum: 64
        maximum: 8192
  
  # 4. 可用实现（自包含，替代原来的 TechStack）
  implementations:
    # 实现1：PortAudio Pro（默认）
    - name: portaudio-pro
      description: "专业 PortAudio 实现"
      platforms: [linux, windows, macos]
      default: true
      wasm-module: "./impl/portaudio-pro.wasm"
      metadata:
        performance: 90
        latency: low
        compatibility: high
      config-defaults:
        portaudio-device: "default"
    
    # 实现2：JACK
    - name: jack
      description: "JACK Audio Connection Kit"
      platforms: [linux, macos]
      wasm-module: "./impl/jack.wasm"
      metadata:
        performance: 95
        latency: very-low
    
    # 实现3：ALSA
    - name: alsa
      description: "ALSA 原生实现"
      platforms: [linux]
      wasm-module: "./impl/alsa.wasm"
    
    # 实现4：Mock（测试用）
    - name: mock
      description: "模拟实现（用于测试）"
      platforms: [all]
      test-only: true
      wasm-module: "./impl/mock.wasm"
  
  # 5. 默认选择策略
  default-strategy:
    preferred: portaudio-pro
    fallbacks: [jack, alsa, mock]
    policy: prefer-low-latency  # 可选: prefer-performance / prefer-compatibility
  
  # 6. 场景预设（可选）
  scene-presets:
    music-production:
      preferred: jack
      fallbacks: [portaudio-pro, alsa]
      config-override:
        sample-rate: 48000
        buffer-size: 64
    
    iot-edge:
      preferred: alsa
      fallbacks: [mock]
      config-override:
        sample-rate: 44100
        buffer-size: 2048
    
    gaming:
      preferred: portaudio-pro
      config-override:
        buffer-size: 256
```

### 2. Application（用户应用配置）

用户通过这个配置文件组合组件，构建自己的应用。

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: Application
metadata:
  name: music-producer-workstation
  version: "1.0.0"
  description: "专业音乐制作人工作站"
  author: "User Name"

spec:
  # 组合组件
  components:
    # 方式1：使用默认配置（最简单）
    - name: audio
      type: yiduo.cap/audio-processing:1.0.0
    
    # 方式2：选择场景预设
    - name: audio-iot
      type: yiduo.cap/audio-processing:1.0.0
      use-scene: iot-edge
    
    # 方式3：自定义实现选择
    - name: audio-custom
      type: yiduo.cap/audio-processing:1.0.0
      implementation:
        preferred: jack
        fallbacks: [portaudio-pro, alsa]
    
    # 方式4：覆盖配置参数
    - name: audio-tuned
      type: yiduo.cap/audio-processing:1.0.0
      config:
        sample-rate: 96000
        buffer-size: 512
    
    # 方式5：完整自定义
    - name: audio-full
      type: yiduo.cap/audio-processing:1.0.0
      use-scene: music-production
      implementation:
        preferred: jack
      config:
        buffer-size: 128  # 覆盖场景预设的部分配置
  
  # 组件间连接（可选）
  connections:
    - from: audio-iot.output
      to: audio-tuned.input
      condition: "config.enabled == true"
```

## 权限系统设计

### 为什么需要权限系统？

虽然 Wasm 提供了沙箱隔离，但我们仍然需要类似 Android 的权限系统，原因：

| 原因         | 说明                   |
| ---------- | -------------------- |
| **声明式声明**  | 组件需要明确声明"我需要访问什么能力"  |
| **用户知情同意** | 用户需要知道并同意组件能访问什么     |
| **细粒度控制**  | 系统需要进行细粒度控制，而不是全有或全无 |
| **安全审计**   | 可以审计组件的权限使用情况        |

### 权限分类

#### 1. 能力权限（Capabilities）

对应组件需要访问的硬件/系统能力：

| 权限               | 说明        | 示例      |
| ---------------- | --------- | ------- |
| `camera.access`  | 访问摄像头     | 拍照、视频录制 |
| `audio.record`   | 访问麦克风     | 录音      |
| `audio.playback` | 播放音频      | 音乐播放    |
| `location.gps`   | 访问 GPS 位置 | 定位服务    |
| `bluetooth`      | 访问蓝牙      | 设备连接    |
| `usb.host`       | 访问 USB 主机 | 外设连接    |

#### 2. 存储权限（Storage）

对文件系统的访问权限：

| 权限                | 说明       |
| ----------------- | -------- |
| `storage.read`    | 读取文件系统   |
| `storage.write`   | 写入文件系统   |
| `storage.private` | 访问组件私有存储 |
| `storage.shared`  | 访问共享存储   |

#### 3. 网络权限（Network）

网络访问权限：

| 权限                 | 说明        |
| ------------------ | --------- |
| `network.internet` | 访问互联网     |
| `network.local`    | 访问本地网络    |
| `network.server`   | 作为服务器监听端口 |

#### 4. 系统权限（System）

系统级别的权限：

| 权限                    | 说明     |
| --------------------- | ------ |
| `system.settings`     | 修改系统设置 |
| `system.notification` | 发送通知   |
| `system.power`        | 电源管理   |
| `system.process`      | 管理进程   |

### 权限配置格式

```yaml
spec:
  permissions:
    # 方式1：简单声明
    - name: audio.playback
      required: true
    
    # 方式2：详细声明
    - name: camera.access
      required: false
      description: "仅在需要拍照功能时使用"
      reason: "用户头像拍摄"
    
    # 方式3：带条件的权限
    - name: network.internet
      required: false
      when: "config.enable-online-features == true"
      description: "仅在启用在线功能时需要"
```

### 权限运行时流程

```
┌─────────────────────────────────────────────────┐
│ 1. 组件声明权限（Component.yaml）                 │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│ 2. 系统验证权限完整性                            │
│    - 检查是否所有 required 权限都被同意           │
│    - 检查权限是否有效                            │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│ 3. 用户授权（首次使用或配置）                     │
│    - 类似 Android 的运行时权限请求                │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│ 4. Wasm 沙箱 + 权限拦截                          │
│    - Wasm 沙箱提供隔离                           │
│    - 权限系统在 WASI 层进行拦截                   │
│    - 只有被授权的权限才能通过                     │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│ 5. 权限审计（可选）                              │
│    - 记录权限使用情况                            │
│    - 异常检测                                    │
└─────────────────────────────────────────────────┘
```

### 与 Wasm/WASI 的关系

| 层次             | 职责                   |
| -------------- | -------------------- |
| **Wasm 沙箱**    | 提供基础隔离，确保代码不能直接访问宿主机 |
| **WASI 接口**    | 提供标准化的系统访问接口         |
| **一多 OS 权限系统** | 在 WASI 之上进行细粒度权限控制   |
| **配置文件声明**     | 提前声明需要什么权限，让用户知情     |

**类比**：

- Wasm 沙箱 = 公寓的大门
- WASI 接口 = 公寓内的设施接口
- 一多 OS 权限系统 = 每个房间的门锁
- 配置文件声明 = 提前告诉用户"我需要进哪些房间"

### 完整示例：相机应用

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: camera-app
  namespace: com.example
  version: "1.0.0"
  description: "简单的相机应用"

spec:
  provides:
    - interface: com.example:camera/ui
  
  # 权限声明
  permissions:
    - name: camera.access
      required: true
      description: "需要摄像头来拍照"
      reason: "核心功能"
    
    - name: storage.write
      required: true
      description: "保存照片到存储"
    
    - name: location.gps
      required: false
      description: "可选：在照片中添加地理位置信息"
      reason: "地理标记功能"
    
    - name: network.internet
      required: false
      description: "可选：上传照片到云端"
      reason: "云同步功能"
  
  requires:
    - name: camera
      interface: yiduo:cap/camera
      required: true
    - name: storage
      interface: yiduo:storage/filesystem
      required: true
    - name: location
      interface: yiduo:cap/location
      required: false
```

## 递归支持

### 递归依赖示例

```yaml
# ==========================================
# 递归树结构
# ==========================================
media-pipeline (应用)
└─ media-processor
   ├─ video-decoder
   │  └─ hw-accel (可选)
   │     └─ [实现: vaapi / nvdec / mock]
   └─ audio-decoder
      └─ [实现: ffmpeg-aac / mock]
```

### 递归验证流程

系统启动时会递归验证整个组件树：

1. 从根组件开始
2. 验证当前组件
3. 递归验证所有依赖组件
4. 检测循环依赖
5. 验证接口匹配
6. 验证平台兼容性
7. 验证实现可用性

### 循环依赖检测

配置系统会自动检测循环依赖：

```yaml
# ❌ 错误示例：循环依赖
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: component-a
spec:
  requires:
    - name: component-b
---
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: component-b
spec:
  requires:
    - name: component-c
---
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: component-c
spec:
  requires:
    - name: component-a  # 循环！
```

检测输出：

```
❌ 检测到循环依赖！
路径:
  component-a → component-b → component-c → component-a
```

## AI 驱动的组件匹配

### 为什么这个配置系统适合 AI？

当前的结构化配置系统完全符合四元架构，为 AI 提供了完美的基础：

| 四元架构               | 一多 OS 对应    | AI 角色                      |
| ------------------ | ----------- | -------------------------- |
| 💭 **配置文件 = 意志**   | 用户需求、意图、选择  | AI 帮助用户**表达意志**（自然语言 → 配置） |
| 🧬 **器官（组件）= DNA** | 功能实体，自带遗传信息 | AI 理解**DNA结构**（组件接口）       |
| 🌳 **树形 = 生长路径**   | 组件组合、依赖树    | AI 帮助**构建树形**（递归匹配）        |
| 🩸 **链式 = 血液系统**   | 接口契约、数据流动   | AI 验证**链式连通**（接口匹配）        |

| 配置特性                                | AI 能力               |
| ----------------------------------- | ------------------- |
| **`provides`** **/** **`requires`** | 精确的接口匹配（链式血液）       |
| **`metadata.description`**          | 语义理解和搜索（理解DNA）      |
| **`scene-presets`**                 | 场景分类和模式识别（学习生长模式）   |
| **`implementations`**               | 根据策略推荐最佳实现（DNA表达选择） |
| **`permissions`**                   | 安全风险评估（意志安全检查）      |
| **`config`** **Schema**             | 参数自动适配（DNA参数调整）     |

### AI 应用场景

#### 1. 自然语言 → 组件组合

**用户输入**：

```
"我想做一个音乐制作应用，需要录音、混音、MIDI 控制，
优先低延迟，兼容 Linux 和 macOS"
```

**AI 处理流程**：

```
1. 理解需求 → 提取关键信息
   - 功能：录音、混音、MIDI
   - 约束：低延迟、Linux/macOS
   
2. 搜索组件库 → 匹配接口
   - audio-processing (提供 audio-record)
   - midi-control (提供 midi-interface)
   - audio-mixer (提供 audio-mix)
   
3. 递归匹配依赖 → 构建组件树
   - audio-processing 
     └─ cpu, memory (required)
     └─ low-latency-io (required)
   - midi-control
     └─ midi-hardware (可选)
   
4. 选择实现 → 根据策略
   - 对于 audio-processing：
     ✅ 首选 jack (低延迟、支持 Linux/macOS)
     ✅ 降级 portaudio-pro
   
5. 生成 Application 配置
```

**AI 输出**：

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: Application
metadata:
  name: ai-generated-music-studio
  description: "AI 生成的音乐制作应用"

spec:
  components:
    - name: audio
      type: yiduo.cap/audio-processing:1.0.0
      use-scene: music-production
      implementation:
        preferred: jack
        fallbacks: [portaudio-pro]
    
    - name: midi
      type: yiduo.cap/midi-control:1.0.0
    
    - name: mixer
      type: yiduo.cap/audio-mixer:1.0.0
```

#### 2. 智能推荐实现

AI 可以根据以下因素推荐最佳实现：

| 因素       | 数据来源                                     |
| -------- | ---------------------------------------- |
| **性能**   | `implementations[].metadata.performance` |
| **平台兼容** | `implementations[].platforms`            |
| **用户偏好** | 历史选择记录                                   |
| **场景适配** | `scene-presets`                          |
| **依赖关系** | 与其他组件的兼容性                                |

**示例决策**：

```
用户需求：IoT 设备，资源受限

AI 推理：
- 考虑：performance=85, latency=low, memory-footprint=small
- 推荐：
  audio-processing → 选择 alsa（轻量）
  network → 选择 lwip（小体积）
```

#### 3. 组件发现与建议

**场景**：用户正在构建智能家居应用，已经选了几个组件

**AI 分析**：

```
当前组件：
  - smart-home-controller
  - zigbee-device-control

AI 发现：
  - 缺少语音控制（可选但推荐）
  - 缺少自动化规则引擎（核心依赖）

AI 建议：

```

#### 4. 自动补全与优化

**场景**：用户写了一半配置

```yaml

kind: Application
metadata:
  name: my-camera-app
spec:
  components:
    - name: camera
      type: yiduo.cap/camera:1.0.0
      # 用户停在这里...
```

## ⚡ 增量验证：只验证变更的组件

### 核心思想

**只重新验证变更的文件！**

### 为什么需要增量验证？

| 场景              | 全量验证   | 增量验证  | 提升      |
| --------------- | ------ | ----- | ------- |
| 单文件变更 (1000 组件) | 1000 次 | 1 次   | 1000x ⚡ |
| 小部分变更 (1%)      | 1000 次 | 10 次  | 100x    |
| 大规模变更 (50%)     | 1000 次 | 500 次 | 2x      |

### 最简单的实现方案

不需要复杂的依赖分析，只需要：

1. **缓存验证结果**
   - 记录每个文件的验证结果
   - 记录文件的修改时间
2. **检查是否需要重新验证**
   ```
   当验证文件时:
     if (文件当前修改时间 > 缓存记录的修改时间):
         重新验证
         更新缓存
     else:
         直接用缓存结果
   ```

### 数据结构

```
缓存条目: {
  文件路径: String
  文件修改时间: Int64  // 时间戳
  验证结果: Bool
  验证时间: Int64
}

验证器: {
  缓存: Map<文件名 -> 缓存条目>
}
```

### 工作流程

```
第一轮验证:
  [验证] audio.yaml  ← 第一次验证
  [验证] camera.yaml ← 第一次验证

第二轮验证 (相同文件):
  [缓存命中] audio.yaml  ← 没变，用缓存
  [缓存命中] camera.yaml ← 没变，用缓存

第三轮验证 (audio.yaml 变更):
  [验证] audio.yaml  ← 变了，重新验证
  [缓存命中] camera.yaml ← 没变，用缓存
```

### 与四元架构的关系

| 四元架构         | 验证系统对应      |
| ------------ | ----------- |
| 💭 配置文件 = 意志 | 验证的输入       |
| 🧬 器官 = DNA  | 验证的对象       |
| 🌳 树形 = 生长路径 | (高级功能，暂不需要) |
| 🩸 链式 = 血液系统 | 接口验证 (单独实现) |

## 与 001 设计原则的对应关系

本规范完全符合 [001.设计原则](file:///d:\yiduo\interfaces\技术文档\001.设计原则：如何做到足够优雅、足够抽象.md) 中的三大核心原则：

### 1. 🔗 链式架构（血液系统）- 根本

| 配置规范特性                  | 对应设计原则        |
| ----------------------- | ------------- |
| WIT 接口定义                | 链式骨架，稳定不变     |
| 命名空间 + 版本               | 清晰的层级关系       |
| 接口契约（provides/requires） | 保证血液（数据/调用）畅通 |

### 2. 🌳 树形架构（生长的器官）- 应变

| 配置规范特性                 | 对应设计原则    |
| ---------------------- | --------- |
| 多实现选择（implementations） | 在链节点上灵活生长 |
| 场景预设（scene-presets）    | 不同器官组合方式  |
| 递归依赖                   | 树状结构，枝繁叶茂 |

### 3. 📋 配置文件即编程（DNA）- 蓝图

| 配置规范特性           | 对应设计原则          |
| ---------------- | --------------- |
| 声明式 YAML 配置      | DNA 蓝图，定义"需要什么" |
| Application 组合配置 | 灵活组合，像编程一样表达需求  |
| 递归验证             | DNA 检测，验证正确性    |

### 三大设计原则的体现

| 原则       | 体现                |
| -------- | ----------------- |
| **简单性**  | 组件小而专一，拆成独立积木     |
| **正交性**  | 组件之间独立，通过接口契约连接   |
| **可组合性** | 配置文件自由组合，解决任意业务需求 |

### 为什么移除"组件继承（extends）"？

设计原则明确指出：**组合优先而非继承**（001 文档第 676 行）。继承会：

- ❌ 破坏简单性：组件变得复杂
- ❌ 破坏正交性：组件之间产生耦合
- ❌ 违背树形架构：继承链可能混乱

✅ **替代方案**：用组件组合（ComponentTemplate）和配置覆盖来实现类似效果

## 📱 与 Android 应用清单的对比

### 核心理念一致性

就像 Android 应用必须包含 `AndroidManifest.xml` 一样，一多 OS 的每个组件都必须包含 `Component.yaml`：

| 方面       | Android               | 一多 OS            |
| -------- | --------------------- | ---------------- |
| **清单文件** | `AndroidManifest.xml` | `Component.yaml` |
| **声明式**  | XML 声明应用信息            | YAML 声明组件信息      |
| **作用**   | 定义应用身份、能力、需求          | 定义组件身份、能力、需求     |

### 详细对比表

#### 1. 基本信息

| AndroidManifest.xml                    | Component.yaml          | 说明      |
| -------------------------------------- | ----------------------- | ------- |
| `<manifest package="com.example.app">` | `namespace: yiduo.cap`  | 包名/命名空间 |
| `android:versionName="1.0.0"`          | `version: "1.0.0"`      | 版本号     |
| `android:label="@string/app_name"`     | `description: "音频处理组件"` | 名称/描述   |

#### 2. 提供的能力

| AndroidManifest.xml                       | Component.yaml                        | 说明          |
| ----------------------------------------- | ------------------------------------- | ----------- |
| `<activity android:name=".MainActivity">` | `provides:`                           | 提供的界面/能力    |
| `<service android:name=".PlayerService">` | `- interface: yiduo:cap/audio-play`   | 提供的服务/接口    |
| `<receiver android:name=".Receiver">`     | `- interface: yiduo:cap/audio-record` | 提供的广播接收器/接口 |
| `<provider android:name=".Provider">`     | (更多接口...)                             | 提供的内容提供器/接口 |

#### 3. 需要的权限

| AndroidManifest.xml                                               | Component.yaml          | 说明     |
| ----------------------------------------------------------------- | ----------------------- | ------ |
| `<uses-permission android:name="CAMERA" />`                       | `permissions:`          | 需要的权限  |
| `<uses-permission android:name="INTERNET" />`                     | `- name: camera.access` | 具体权限声明 |
| `<uses-permission android:name="RECORD_AUDIO" />`                 | `- name: audio.record`  | 具体权限声明 |
| `<uses-feature android:name="camera" android:required="false" />` | `required: false`       | 可选权限声明 |

#### 4. 需要的依赖

| AndroidManifest.xml | Component.yaml   | 说明      |
| ------------------- | ---------------- | ------- |
| (无直接对应)             | `requires:`      | 需要的组件依赖 |
| (通过 Gradle 依赖)      | `- name: cpu`    | 需要的具体组件 |
| (通过 Gradle 依赖)      | `- name: memory` | 需要的具体组件 |

#### 5. 实现选择（一多 OS 特有）

| 一多 OS               | 说明                                           |
| ------------------- | -------------------------------------------- |
| `implementations:`  | 组件可用的实现（类似 Android 的 `minSdkVersion` 适配不同版本） |
| `default-strategy:` | 默认选择策略（类似 Android 的首选配置）                     |
| `scene-presets:`    | 场景预设（类似 Android 的不同配置变体）                     |

### 示例对比

#### AndroidManifest.xml 示例

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.example.musicplayer"
    android:versionName="1.0.0">

    <application
        android:label="音乐播放器"
        android:description="专业的音乐播放应用">

        <!-- 提供的能力 -->
        <activity android:name=".MainActivity" />
        <service android:name=".PlayerService" />

        <!-- 需要的权限 -->
        <uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE" />
        <uses-permission android:name="android.permission.INTERNET" />

        <!-- 需要的硬件特性 -->
        <uses-feature android:name="android.hardware.audio.output" />

    </application>
</manifest>
```

#### Component.yaml 示例（对应）

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: music-player
  namespace: com.example
  version: "1.0.0"
  description: "专业的音乐播放组件"

spec:
  # 提供的能力（对应 <activity>, <service>）
  provides:
    - interface: com.example:player/ui
    - interface: com.example:player/playback

  # 需要的依赖（对应 <uses-permission>, <uses-feature>）
  requires:
    - name: storage
      interface: yiduo:storage/filesystem
      required: true
    - name: network
      interface: yiduo:network/http
      required: true
    - name: audio
      interface: yiduo:cap/audio-play
      required: true

  # 配置参数
  config:
    schema:
      type: object
      properties:
        default-volume: { type: float, default: 0.8 }

  # 可用实现（一多 OS 特有）
  implementations:
    - name: gstreamer-player
      default: true
    - name: ffmpeg-player
    - name: mock
      test-only: true

  # 默认策略
  default-strategy:
    preferred: gstreamer-player
    fallbacks: [ffmpeg-player, mock]
```

### 为什么选择 YAML 而不是 XML？

| 方面           | XML（Android） | YAML（一多 OS）                        |
| ------------ | ------------ | ---------------------------------- |
| **可读性**      | 较繁琐，标签嵌套深    | 简洁，层次清晰                            |
| **书写体验**     | 需要闭合标签       | 缩进即可，更快捷                           |
| **生态**       | Android 生态使用 | Kubernetes、Docker Compose 等云原生生态使用 |
| **与 WIT 配合** | 一般           | YAML + WIT 的组合更现代                  |

### 关键差异

| 方面       | Android  | 一多 OS            |
| -------- | -------- | ---------------- |
| **粒度**   | 整个应用一个清单 | 每个组件一个清单         |
| **递归**   | 清单文件不递归  | 组件可以递归依赖其他组件     |
| **多实现**  | 主要是版本适配  | 每个组件可以有多个完全不同的实现 |
| **策略配置** | 通过资源配置适配 | 内置策略配置和场景预设      |

### 总结

**是的！这个配置系统确实类似 Android 应用清单，但更强大！**

- ✅ **灵感相同**：都是声明式的清单文件，定义"我是谁"、"我能做什么"、"我需要什么"
- ✅ **但更强大**：支持递归依赖、多实现选择、策略配置、场景预设
- ✅ **更现代**：使用 YAML，借鉴 Kubernetes 等云原生技术的成熟经验
- ✅ **组件化**：不仅是应用，每个小组件都有自己的清单
