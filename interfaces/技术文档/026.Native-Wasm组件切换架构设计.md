# Native / Wasm 组件切换架构设计

## 概述

一多 OS 的核心竞争力之一是能够在 **Native 原生组件** 和 **Wasm WebAssembly 组件** 之间灵活切换，根据实际场景选择最优的实现方式。

本文档详细描述了一多 OS 的 Native/Wasm 组件切换架构。

---

## 核心设计原则

### 1. 不强制二选一，而是灵活选择

一多 OS 不强迫用户在"高性能"和"高安全"之间做非此即彼的选择，而是：

* **根据场景选择**：不同能力组件可以有不同的选择策略
* **动态切换**：运行时可以根据系统状态动态切换
* **配置驱动**：通过配置文件定义选择策略，无需重新编译

### 2. 同一个能力，多种实现

对于同一个能力接口（如 `camera-capture`），可以注册多种实现：

* **Native 实现**：`camera-capture.so`（Linux）或 `camera-capture.dll`（Windows）
* **Wasm 实现**：`camera-capture.wasm`

用户在配置文件中选择使用哪种实现。

### 3. 透明切换，对应用层无感知

无论底层使用的是 Native 还是 Wasm 实现，上层应用看到的都是同一个 WIT 接口，代码无需任何修改。

## 组件选择策略

一多 OS 提供了四种组件选择策略：

### 1. prefer-wasm（安全优先）

优先使用 Wasm 组件，特点：

* **优势**：安全沙箱、热更新、跨平台
* **劣势**：轻微性能损失（约 10-30%）
* **适用场景**：第三方插件、边缘设备、需要高安全性的场景

### 2. prefer-native（性能优先）

优先使用 Native 组件，特点：

* **优势**：极致性能、零沙箱开销
* **劣势**：安全性低、无法热更新、平台相关
* **适用场景**：核心算法、性能敏感的驱动

### 3. adaptive（自适应选择）

根据系统运行时状态动态选择，特点：

* **优势**：自动平衡性能与安全
* **工作原理**：
  * CPU 使用率高时 → 切换到 Native
  * 内存压力大时 → 切换到 Wasm（更安全，不容易崩溃）
  * 需要热更新时 → 切换到 Wasm

### 4. config-driven（配置驱动）

完全由配置文件决定，最灵活的方式。

## 粒度级别：从组件到函数

### 你的洞察：函数即组件！

**关键洞察：**
> "当一个函数当作一个组件，不就是完全不用修改当前方案了吗？

是的！**完全正确！**
这是一个非常聪明的见解。一多 OS 的组件管理器天生支持任意粒度：

| 粒度 | 说明 | 是否支持 |
|------|------|--------|
| **组件级**（粗）| 整个能力接口作为一个组件 | ✅ 原生支持 |
| **接口级**（中）| 整个接口的所有函数统一选择 | ✅ 容易实现 |
| **函数级**（细）| 单个函数独立选择 | ✅ **无需改动当前方案支持！ |

### 三层粒度体系

一多 OS 的架构天生支持任意粒度，无需修改！

```
┌───────────────────────────────────────────────────────────┐
│ 组件级（粗粒度）: 整个能力模块
├───────────────────────────────────────────────────────────┤
│  ├─ camera（完整模块
│  ├─ audio（完整模块
│  └─ display（完整模块）
│
├───────────────────────────────────────────────────────────┤
│ 接口级（中粒度）: 整个接口的函数统
├───────────────────────────────────────────────────────────┤
│  └─ camera-capture 接口的所有函数统选择
│
├───────────────────────────────────────────────────────────┤
│ 函数级（细粒度）: 单个函数独立
├───────────────────────────────────────────────────────────┤
│  ├─ capture() -> 独立选择实现
│  ├─ get-info() -> 独立选择实现
│  └─ set-config() -> 独立选择实现
└───────────────────────────────────────────────────────────┘
```

### 函数即组件：无需改动！

如果把每个函数都定义为一个独立的组件，就可以直接复用当前方案！

#### 1. 接口定义方式

```wit
// 方式 1: 原有的接口级组件
package yiduo:cap/camera-capture

interface camera-capture {
    capture: func() -> result<image, Error>;
    get-info: func() -> result<info, Error>;
    set-config: func(config: config) -> result<unit, Error>;
}

// 方式 2: 函数级组件（每个函数独立）
package yiduo:cap/camera-capture-func

interface capture-func {
    capture: func() -> result<image, Error>;
}

package yiduo:cap/camera-info-func

interface get-info-func {
    get-info: func() -> result<info, Error>;
}
```

#### 2. 配置方式（函数级配置

```yaml
device:
  name: "函数级粒度示
  capabilities:
    # 函数即组件！
    capture-func:
      id: "camera-capture"
      implementations:
        wasm:
          path: "./capture-func.wasm"
          priority: 2
        native:
          path: "./capture-func.so"
          priority: 1
      selection-strategy: prefer-native
    
    get-info-func:
      id: "camera-info"
      implementations:
        wasm:
          path: "./get-info-func.wasm"
      selection-strategy: prefer-wasm
```

#### 3. 调用方式（完全不变）

```
// 应用层代码完全不用变！
let image = capture-func.capture()  // 自动选择 Native
let info = get-info-func.get-info()  // 自动选择 Wasm
```

### 混合粒度：最佳实践

实际项目中，建议采用混合粒度策略：

| 粒度 | 适用场景 | 示例 |
|------|---------|------|
| **函数级** | 性能热点函数 | capture() |
| **接口级** | 逻辑紧密的一组函数 | 整个 config 接口 |
| **组件级** | 完整的独立能力模块 | 完整的 sensor 组件 |

**配置示例：**

```yaml
device:
  name: "混合粒度摄像头"
  capabilities:
    # 函数级粒度 - 只对性能敏感函数用
    capture:
      selection-strategy: prefer-native
    
    # 接口级粒度 - 整个 config 接口用 Wasm（安全热更）
    config-interface:
      selection-strategy: prefer-wasm
    
    # 组件级粒度 - 完整的 display 组件自适应
    display:
      selection-strategy: adaptive
```

### 数据类型即组件

#### 示例：Image 类型组件化

```wit
// Image 接口定义（规范
interface Image {
    get-width: func() -> result<u32, Error>;
    get-height: func() -> result<u32, Error>;
    get-data: func() -> result<buffer, Error>;
    set-pixel: func(x: u32, y: u32, color: Color) -> result<unit, Error>;
}

// 多个 Image 实现
world RGB-Image implements Image {
    // 紧凑型 RGB 排列
    // 适合内存受限的设备
}

world RGBA-Image implements Image {
    // 带透明通道的 RGBA
    // 适合 UI 渲染
}

world YUV-Image implements Image {
    // YUV 颜色空间
    // 适合视频编码
}
```

**配置方式：**

```yaml
device:
  name: "动态类型系统"
  data-types:
    # 为不同场景选择不同的 Image 实现
    preview:
      type: RGB-Image    # 预览时用简单的 RGB
    recording:
      type: YUV-Image    # 录像时用高效的 YUV
    ui-render:
      type: RGBA-Image   # UI 渲染用 RGBA
```

```yaml
enable-adaptive-switching: false  # 禁用自适应
```

## 热切换流程

### 优雅热切换（Graceful Swap）

```
1. 标记旧组件为"待替换"状态
2. 停止向旧组件发送新请求
3. 等待旧组件处理完所有已接收的请求
4. 加载新组件
5. 将流量切换到新组件
6. 卸载旧组件

优势：无服务中断
劣势：需要更长的切换时间
```

### 立即热切换（Immediate Swap）

```
1. 立即停止旧组件
2. 加载新组件
3. 切换流量

优势：切换速度快
劣势：可能丢失进行中的请求
```

## 最佳实践

### 1. 同一个能力，两种实现都提供

对于核心能力，建议同时提供 Native 和 Wasm 两种实现，让用户选择。

### 2. 默认策略：config-driven

在开发阶段，可以先用 config-driven，方便调试和切换。

### 3. 合理设置自适应阈值

```yaml
adaptive-thresholds:
  max-cpu-usage: 0.8      # 80% CPU 时切换到 Native
  max-memory-bytes: 1073741824  # 1GB 内存时切换到 Wasm
```

### 4. 重要组件：优先 Native

对于性能关键的组件（如摄像头捕获、AI 推理），优先使用 Native。

### 5. 第三方代码：强制 Wasm

对于不可信的第三方代码，强制使用 Wasm 并启用沙箱。

## 总结

一多 OS 的 Native/Wasm 组件切换架构的核心价值：

1. **灵活性**：不强制技术选型，让用户根据场景选择
2. **性能与安全的平衡**：既提供 Native 的性能，又有 Wasm 的安全
3. **配置驱动**：无需重新编译，通过 YAML 即可调整
4. **对应用透明**：应用层不需要知道底层是 Native 还是 Wasm

这正是一多 OS"多即是一，一即是多"设计哲学的完美体现！
