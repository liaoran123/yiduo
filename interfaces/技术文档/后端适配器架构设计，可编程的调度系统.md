# 后端适配器架构设计：可编程的调度系统

## 概述

一多 OS 的 WIT 接口是**标准接口定义**，但实际功能需要通过**后端适配器（Backend Adapter）**来对接现有的成熟库。

**重要的是：后端适配器不只是简单的适配器，而是一个可编程的调度系统！**

---

## 从"适配器"到"可编程调度系统"

### ❌ 原来的理解（不够深刻）
- 只是"对接现有的库"
- 简单的一对一映射
- 静态的实现选择

### ✅ 现在的理解（正确的）
- **可编程的调度系统**
- 动态选择最合适的实现
- 支持策略、规则、优先级

---

## 可编程调度系统的特性

### 1. 动态选择
- 根据硬件、场景、性能自动选择最佳后端
- 例如：摄像头设备 → 优先选择 libcamera，没有则降级为 OpenCV

### 2. 策略配置
- 可配置的调度策略
- 例如：优先性能 / 优先兼容性 / 优先兼容性

### 3. 降级方案
- 主要后端不可用时，自动降级到备选后端
- 例如：硬件加速失败 → 回退到软件实现

### 4. 可观测性
- 可以查看当前使用的后端
- 可以监控性能指标
- 可以调试和优化

## 可编程调度系统的实现思路

### 配置驱动的调度
```yaml
device:
  name: "智能摄像头"
  capabilities:
    camera:
      # 配置后端选择策略
      backend-strategy: "prefer-native"
      # 优先级排序
      backends:
        - name: libcamera
          priority: 10
          native: true
        - name: opencv
          priority: 5
          fallback: true
        - name: mock
          priority: 1
          test-only: true
```

### 可编程的调度逻辑
```
调度流程：
1. 读取配置的策略和优先级
2. 按优先级尝试每个后端
3. 检查后端是否可用（硬件支持、库存在）
4. 选择第一个可用的后端
5. 如果所有后端都不可用，报错或降级
```

## 与三大设计原则的完美契合

### 1. 链式是血液（稳定的基础接口层）

```
┌─────────────────────────────────────────────────────┐
│      一多 OS WIT 接口（稳定、不变化）             │ ← 链式血液
│  (标准接口定义，像生物的遗传物质一样稳定)       │
└─────────────────────────────────────────────────────┘
```

**体现：**
- WIT 接口是稳定的"血液"层
- 无论后端怎么变，接口保持一致
- 就像生物的 DNA 代码稳定不变

---

### 2. 树形是器官（可替换的后端实现）

```
┌─────────────────────────────────────────────────────┐
│           WIT 接口（标准定义）               │ ← 链式血液
└──────────────────────┬────────────────────────────┘
                       │
┌──────────────────────┴────────────────────────────┐
│   ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│   │ Libcam   │  │  OpenCV  │  │   Mock   │   │ ← 树形器官
│   │ Backend  │  │ Backend  │  │ Backend  │   │ (不同的实现)
│   └──────────┘  └──────────┘  └──────────┘   │
└─────────────────────────────────────────────────────┘
```

**体现：**
- 同一个 WIT 接口可以有多个后端实现
- 不同的后端像不同的器官（肝、肾、心）
- 可以根据需要选择/替换/组合

---

### 3. 配置即DNA（配置决定使用哪个后端）

```yaml
device:
  name: "示例设备"
  backends:
    camera:
      default: libcamera    # DNA 决定用哪个器官
      fallbacks:
        - opencv
        - mock
```

**体现：**
- 配置文件像 DNA 一样决定系统行为
- 用户可以选择用哪个后端实现
- 同一个接口，不同配置有不同的表现

| 原则 | 后端适配器架构 | 类比 |
|------|-------------|------|
| **链式是血液** | 标准 WIT 接口层 | 遗传物质（DNA），稳定不变 |
| **树形是器官** | 多种后端适配器实现 | 不同的器官，可替换 |
| **配置即DNA** | YAML 配置选择后端 | 基因型决定表现型 |

**完全符合设计理念！** 🎉

## 总结

### 核心思想

**不是重新发明轮子，而是把现有轮子装到我们的车上！**

- WIT 接口 = 标准化的轮子接口
- 后端适配器 = 把轮子装到车上的零件
- 现有库 = 现成的好轮子

### 实施优先级

1. ✅ **先做 Mock 后端** - 让系统跑起来
2. ✅ **再做 Linux 桌面后端** - 验证概念
3. ✅ **然后做嵌入式后端** - 走向真正产品
4. ✅ **其他平台** - 有资源再做

### 关键优势

- 不需要从零写驱动
- 可以利用成熟生态
- 测试方便（Mock 后端）
- 可以支持多种后端，用户选择最合适的

## 借鉴 Kubernetes/Docker Compose 的成熟经验

### 为什么要借鉴 K8s/Compose？

| 方面 | K8s/Compose 理念 | 我们的应用 |
|------|-----------------|----------|
| **配置文件即编程** | 用 YAML 声明式定义"我需要什么" | 用 YAML 声明式选择后端 |
| **关注点分离** | YAML = 声明 / Controller = 执行 | 配置 = 声明 / 调度器 = 执行 |
| **可验证性** | `kubectl apply --dry-run` | `yiduo-device apply --dry-run` |
| **健康检查** | Readiness/Liveness Probes | 后端健康检查与自动修复 |
| **容错机制** | ReplicaSet、自动重启 | 后端 Fallback、降级策略 |

### 借鉴点 1：声明式优先的配置设计

#### K8s 风格的 YAML 配置
```yaml
apiVersion: yiduo.dev/v1alpha1
kind: DeviceSpec
metadata:
  name: smart-camera
  labels:
    device-type: camera
    vendor: sony
    model: imx327

spec:
  # 能力声明（像 K8s 的 Pod 规格）
  capabilities:
    - name: camera
      backend:
        # 主后端
        primary: libcamera
        # 降级选项（像 K8s 的 Pod 反亲和性）
        fallbacks:
          - opencv
          - mock
        # 选择策略
        strategy: prefer-native
        # 健康检查（像 K8s 的 Probes）
        healthCheck:
          enabled: true
          intervalSeconds: 10
          timeoutSeconds: 3
          failureThreshold: 3

    - name: audio
      backend:
        primary: pulseaudio
        fallbacks:
          - alsa
          - mock
        strategy: prefer-compatibility

    - name: display
      backend:
        primary: wayland
        fallbacks:
          - x11
          - mock
        strategy: prefer-performance
```

#### 核心配置字段说明
| 字段 | 说明 | 借鉴来源 |
|------|------|---------|
| `primary` | 首选后端 | K8s 首选调度节点 |
| `fallbacks` | 降级选项 | K8s 节点亲和性降级 |
| `strategy` | 选择策略 | K8s 调度策略 |
| `healthCheck` | 健康检查配置 | K8s Readiness/Liveness |

### 借鉴点 4：健康检查与容错机制

#### 后端健康检查（像 K8s Probes）
```yaml
spec:
  capabilities:
    - name: camera
      backend:
        primary: libcamera
        fallbacks: [opencv, mock]
        # 健康检查配置
        healthCheck:
          enabled: true
          # 探测间隔（秒）
          intervalSeconds: 10
          # 超时时间（秒）
          timeoutSeconds: 3
          # 连续失败多少次触发降级
          failureThreshold: 3
          # 恢复阈值
          successThreshold: 2
          # 探测命令
          probe:
            type: exec
            command: ["camera-check"]
```

#### 容错机制
```yaml
spec:
  capabilities:
    - name: camera
      backend:
        primary: libcamera
        fallbacks: [opencv, mock]
        # 容错策略
        faultTolerance:
          # 自动降级
          autoFallback: true
          # 自动恢复
          autoRecovery: true
          # 恢复等待时间（秒）
          recoveryDelaySeconds: 60
```

### 完整的借鉴总结表

| K8s/Docker Compose 概念 | 我们的应用 | 文档位置 |
|----------------------|---------|---------|
| **Deployment** | DeviceSpec YAML | `device-spec.yaml` |
| **Pod** | 后端实例 | LibcameraBackend 等 |
| **Scheduler** | 后端调度器 | 可编程调度系统 |
| **Probes** | 健康检查 | `healthCheck` 配置 |
| **NodeSelector** | 后端选择策略 | `strategy` 配置 |
| **Affinity** | 后端优先级 | `primary/fallbacks` |
| **Dry Run** | 配置验证 | `yiduo-device validate` |
| **Status** | 后端状态 | `yiduo-device status` |

## 为什么这样设计是正确的？

### 1. 站在巨人肩膀上
- K8s/Docker Compose 已经验证了这套模式的成功
- 开发者已经熟悉这种工作流
- 可以复用很多工具链的设计思想

### 2. 用户体验一致性
- 熟悉 `kubectl` 的开发者可以快速上手
- YAML 配置符合云原生时代的习惯
- 声明式思维已经被广泛接受

### 3. 可扩展性
- 这套模式已经在大规模生产环境中验证
- 可以支持复杂的调度策略和容错机制
- 可以支持多设备、分布式场景
