# 🌳 设计原则：树形操作系统架构（如何做到足够优雅、足够抽象）

> **核心原则**：只要 `interfaces/` 目录（树干）设计得足够优雅、足够抽象，整个系统的复杂度就会被死死地锁在那个小小的目录里，而不会扩散到整个代码库！

---

## 🌱 核心理念：树形操作系统架构（分叉即枝叶）

这个架构的设计灵感来自软件行业最成熟的实践，**本质上是一棵树的生长**，不仅适用于接口层，而是整个操作系统项目的架构思想！

| 树形比喻 | 架构对应 | 说明 |
|---------|---------|------|
| 🌱 **树根** | interfaces/ | 完全稳定，永不修改，一切的基础 |
| 🌿 **树干** | kernel/ + runtime/ | 从树根往上长，核心系统层 |
| 🌳 **树枝** | services/ | 系统服务层，提供各种功能 |
| 🍃 **树叶** | apps/ | 具体应用层，通过组合服务实现 |
| � **向外生长** | 添加新功能 | 只分叉新枝叶，不破坏主干 |
| 🚫 **不砍树** | 不删不改 | 只增不改 |

### 设计灵感来源

- **HTML 演进**：5 个版本，30 年历史，就像一棵树越长越大，永不破坏主干
- **Android API**：35 个层级，向后兼容，树枝越长越茂盛
- **Linux 系统调用**："不要破坏用户空间"，树干永远不动
- **POSIX 标准**：跨平台兼容典范，树干相同，枝叶可以不同

### 整个操作系统项目的树形原则

1. **🌱 树根永远不动**：`interfaces/` 作为树根，定义后保持稳定，只增不改
2. **🌿 树干依赖树根**：`kernel/` 和 `runtime/` 必须完整实现和依赖 `interfaces/`
3. **🌳 树枝依赖树干**：`services/` 必须完整依赖 `kernel/` 和 `runtime/` 的能力
4. **🍃 树叶依赖树枝**：`apps/` 只能通过 `services/` 和 `interfaces/` 来访问系统
5. **⚠️ 只增不改**：所有层都只能新增功能，不能修改或删除现有功能

### 📋 树形架构核心规则（植树守则）

1. **🌱 树干永存**：所有组件共享同一个根接口（第0层），完全冻结，永不修改
2. **🌿 树枝继承**：每一层必须完整包含上一层的所有接口（树从树干往上长）
3. **🍃 只向外分叉**：只能添加新接口，不能修改或删除现有接口（树干不动，只长新叶）
4. **🔗 枝枝相连**：前一个衔接上一个，不会从中间断裂
5. **⚠️ 只增不改**：绝对禁止砍树、改树，只能种树

## ⚠️ 重要警告：破坏性分叉 vs 健康分叉

### ❌ 错误方式：版本化分叉（砍树）

**比喻**：把树砍成两半，一半叫"旧树"，一半叫"新树"

```
  版本化分叉示意图
  ────────────────────
  v1.0 发布 → v1.1 发布（砍树1）→ v2.0 发布（砍树2）→ v3.0 发布（砍树3）

  结果：
  - 🌳🌳🌳 变成好几棵树，需要同时维护
  - 🔧 每次修bug要在好几棵树上改
  - 😕 开发者不知道该爬哪棵树
  - 💀 最终变成"森林债务"

  真实案例：
  - Python 2 vs Python 3：20 年的分叉之痛
  - Web 浏览器兼容性：无数棵树，兼容性噩梦
```

### ✅ 正确方式：健康分叉（枝叶生长）

**比喻**：在同一棵树上长出新枝叶，永远只有一棵树

```
  健康分叉示意图
  ─────────────────
  初始树 → 在树枝上长出新叶 → 再长出新枝 → 树越长越大

  结果：
  - 🌳 永远只有一棵树
  - 🔧 修bug只需要在这棵树上改
  - 😊 开发者知道永远爬这棵树
  - ✨ 树越长越大，功能越来越丰富

  接口演进原则（植树守则）：
  1. 只能添加新的接口/方法，不能修改或删除现有
  2. 新方法使用新的名字，不覆盖旧方法
  3. 提供默认实现，让旧代码继续工作
  4. 用能力发现来检测新功能是否可用
  5. 第 0 层根接口：完全冻结，永不修改（树干不动）
```

### 🎯 树形设计原则

- **下层不能依赖上层**：树干不依赖树叶，树根稳固
- **同一层内可以互用**：树叶之间可以互相连接
- **层次越下越稳定**：树干永远不变，树叶可以生长
- **每层必须包含上一层**：树枝必须包含树干，保持完整性
- **⚠️ 只增不改**：所有层只能添加，不能修改或删除现有接口（不砍树）

## 🌿 接口隔离原则：每片叶子独立生长

### ❌ 反模式：巨叶接口（一片叶子占满整棵树）

```wit

```

### ✅ 优雅模式：每片叶子独立，单一职责

```wit
// ✅ 每个接口是独立的叶子，只做一件事

// 1. 摄像头核心功能（主叶）
interface camera-core {
    resource device {
        capture() -> result<image, error>;
        start-recording() -> result<unit, error>;
        stop-recording() -> result<unit, error>;

    open(id: string) -> result<device, error>;

// 2. 电源管理能力（独立叶）
interface power-capability {
    set-low-power-mode(enabled: bool) -> result<unit, error>;
    get-power-consumption() -> result<u32, error>;
}

// 3. 诊断能力（独立叶）
interface diagnostic-capability {
    get-temperature() -> result<f32, error>;
    run-self-test() -> result<bool, error>;
}

// 🎯 组合：把叶子拼成一束
world smart-camera {
    export camera-core;
    export power-capability;
    export diagnostic-capability;
}
```

## 🌱 演进策略：只长新叶，不改旧叶

### ❌ 反模式：修改/砍掉旧叶

```wit
// ❌ 不要这样做！会破坏整棵树
interface camera {
    // 旧代码：capture()
    // 新代码：直接修改为 capture(config) → 砍掉旧叶！
    capture(config: capture-config) -> result<image, error>;
}
```

### ✅ 优雅方案 1：只长新叶，保留旧叶

```wit
// ✅ 应该这样做！只长新叶，保留旧叶
interface camera-core {
    resource device {
        // 保留旧叶，永不修改！
        capture() -> result<image, error>;

        // 添加新叶，使用新名字！
        capture-with-config(config: capture-config) -> result<image, error>;
    }
}
```

### ✅ 优雅方案 2：能力发现（优雅地检测新叶）

```wit
// 能力发现接口（让应用优雅地知道树长出了新叶）
interface capability-discovery {
    // 检测新叶是否长出来了
    has-feature(feature-name: string) -> result<bool, error>;

    // 获取新叶的描述
    get-feature-description(feature-name: string) -> result<string, error>;

    // 列出树上所有叶子
    list-features() -> result<list<string>, error>;
}

// 使用示例（优雅地使用新叶）
fn take-photo(camera: camera) -> result<image, error> {
    // 优先用新叶（如果长出来了）
    if (camera.has-feature("capture-with-config")) {
        return camera.capture-with-config(high-quality-config);
    }

    // 回退到旧叶（保证兼容）
    return camera.capture();
}
```


## 🎯 总结：树形架构10个黄金法则

| 法则 | 树形比喻 | 内容 | 怎么实现 |
|------|---------|------|---------|
| 1️⃣ | **树干永存** | 链表式层级，每层包含上一层 | 每层必须包含下层 |
| 2️⃣ | **根基统一** | 所有组件都有相同的根接口 | 第0层永远不变 |
| 3️⃣ | **只长新叶** | 只增不改，不能砍树 | 只能新增，不能修改删除 |
| 4️⃣ | **避免砍树** | 避免版本化分叉 | 用新名字添加，不搞版本分支 |
| 5️⃣ | **能爬全树** | 能力发现优雅检测新功能 | 用 has-feature 检测可用性 |
| 6️⃣ | **叶叶独立** | 接口隔离，单一职责 | 每个接口只做一件事 |
| 7️⃣ | **面向树干** | 面向能力抽象，不绑定具体树 | 抽象能力，不绑定具体硬件 |
| 8️⃣ | **拼接树冠** | 组合优先，不用继承 | 接口组合而非继承 |
| 9️⃣ | **树体稳固** | 类型安全，不用通用类型 | 强类型设计 |
| 🔟 | **简单最美** | KISS 原则，少即是多 | 保持简洁 |

## 📊 树形操作安全指南

| 操作 | 能否 | 树形比喻 | 风险 |
|------|-----|---------|------|
