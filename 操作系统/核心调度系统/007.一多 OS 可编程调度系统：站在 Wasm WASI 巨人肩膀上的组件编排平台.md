## 📌 **命名说明
本文档曾用名："后端架构"，但"后端"这个词太狭义了！实际上这不是简单的"后端"，而是整个系统的**可编程调度系统——一多 OS 的核心大脑！

## 概述

一多 OS 的 WIT 接口是**标准接口定义**，但实际功能需要通过**实现提供者（Implementation Provider）** 来对接现有的成熟库。但这不只是一个架构文档，更是**一多 OS 系统内编程的核心调度核心层**！

## 第一步：从组件配置文件开始

在一多 OS 中，**一切都是组件**！从底层的硬件接口到顶层的应用场景，都是组件。这是你接触系统的第一层。

### 核心概念

| 概念 | 说明 |
|------|------|
| **组件** | 一多 OS 中一切事物的统一称呼 |
| **接口** | 组件之间的契约（WIT 定义） |
| **提供** (`provides`) | 这个组件具备哪些能力 |
| **需要** (`requires`) | 这个组件需要哪些其他组件 |
| **实现** (`implementations`) | 每个组件可以有多个实现（类似之前的"后端"） |

### 配置系统简介

一多 OS 的配置系统**完全建立在 Wasm 生态的两个标准机制基础上进行扩展**，而不是重新发明：

#### 📄 基础 1：WIT 接口定义（Wasm Component Model 标准）
```wit
package mycompany:math

interface calculator {
  add: func(a: u32, b: u32) -> u32
}

world math-world {
  export calculator          // "我能做什么"
  import wasi:clocks/wall-clock  // "我需要什么"
}
```

#### 🔗 基础 2：Wasm Component 组件组合（Wasm Component Model 标准）
```yaml
components:
  - name: main-app
    component: ./main.wasm
    imports:
      calculator: lib-calculator
      logger: my-logger
```

#### 🚀 一多 OS 扩展：高级配置与调度（一多 OS 特有）
```yaml
components:
  - name: main-app
    type: wasm
    component: ./main.wasm
    requires:
      - name: calculator
        preferred-implementation: lib-calculator-v2
        fallback-implementations: [lib-calculator-v1, mock-calculator]
    health-check:
      enabled: true
      interval: 10s
```

**一多 OS 配置 = WIT + 组件组合 + 高级调度扩展！**

#### 📊 Wasm 标准 vs 一多 OS 扩展对比表

| 能力 | Wasm Component Model 标准 | 一多 OS 扩展 | 说明 |
|-----|-------------------------|------------|------|
| **声明"我是谁"** | ✅ WIT `package` + `world` | - | 标准已支持 |
| **声明"我能做什么"** | ✅ WIT `export` | - | 标准已支持 |
| **声明"我需要什么"** | ✅ WIT `import` | - | 标准已支持 |
| **组件组合** | ✅ Component Linking | - | 标准已支持 |
| **声明"用哪个实现"** | ❌ | ✅ `preferred-implementation` | 一多 OS 特有 |
| **降级策略** | ❌ | ✅ `fallback-implementations` | 一多 OS 特有 |
| **健康检查** | ❌ | ✅ 健康监控与自动修复 | 一多 OS 特有 |
| **场景预设** | ❌ | ✅ 预配置的场景模板 | 一多 OS 特有 |
| **递归验证** | ❌ | ✅ 循环依赖/平台兼容性检查 | 一多 OS 特有 |
| **动态切换** | ❌ | ✅ 运行时切换实现 | 一多 OS 特有 |

### 配置系统的关键特性

1. **递归结构**：组件可以依赖其他组件，形成树形结构
2. **多实现支持**：每个依赖可以有多个实现
3. **策略选择**：支持 `preferred` + `fallbacks` 策略
4. **场景预设**：为常见场景提供预配置
5. **递归验证**：自动验证接口匹配、循环依赖、平台兼容等

## 一多 OS 与 Wasm/WASI 的完美分工

一多 OS 的定位是**智能调度与整合专家**，与 Wasm/WASI 生态形成完美互补：

### 基础设施层：Wasm/WASI 生态复用
一多 OS 直接采用 Wasm/WASI 生态提供的成熟基础设施：
- **运行时安全隔离**：基于 WebAssembly 的沙箱机制
- **跨平台系统调用**：通过 WASI 标准接口访问文件、网络、时钟等系统资源
- **组件化架构**：采用 Wasm Component Model 实现功能模块的隔离与组合
- **内存管理**：使用 WebAssembly 的线性内存模型

### 核心价值层：一多 OS 的创新领域
一多 OS 专注于提供差异化的核心能力：
- **领域标准接口定义**：通过 WIT 定义 `yiduo:hw-camera`、`yiduo:ai-inference` 等行业级标准接口
- **可编程调度与策略引擎**：实现计算资源（如 AI 模型在 CPU/GPU/NPU 间）的智能调度与后端实现的动态适配
- **声明式配置与动态组装**：通过 YAML 配置文件实现组件的声明式组合与部署
- **健康监测与容错机制**：提供系统运行时监控、自动降级与恢复能力

### 架构优势
这种分层设计具有显著优势：
- **关注点分离**：一多 OS 专注于调度与整合，底层基础设施复用成熟生态
- **生态协同**：与 Wasm/WASI 形成互补，避免重复实现
- **向前兼容**：当 WASI 标准演进时，上层 WIT 定义与调度逻辑保持稳定，仅需调整适配器层即可无缝对接

## 可编程调度系统的特性

### 1. 动态选择
- 根据硬件、场景、性能自动选择最佳后端
- 例如：摄像头设备 → 优先选择 libcamera，没有则降级为 OpenCV

### 2. 策略配置
- 可配置的调度策略
- 例如：优先性能 / 优先兼容性 / 优先兼容性

### 3. 降级方案
- 主要后端不可用时，自动降级到备选后端
- 例如：硬件加速失败 → 回退到软件实现

### 4. 可观测性
- 可以查看当前使用的后端
- 可以监控性能指标
- 可以调试和优化

## 可编程调度系统的实现思路

### 配置驱动的调度
```yaml
device:
  name: "智能摄像头"
  capabilities:
    camera:
      # 配置后端选择策略
      backend-strategy: "prefer-native"
      # 优先级排序
      backends:
        - name: libcamera
          priority: 10
          native: true
        - name: opencv
          priority: 5
          fallback: true
        - name: mock
          priority: 1
          test-only: true
```

### 可编程的调度逻辑
```
调度流程：
1. 读取配置的策略和优先级
2. 按优先级尝试每个后端
3. 检查后端是否可用（硬件支持、库存在）
4. 选择第一个可用的后端
5. 如果所有后端都不可用，报错或降级
```

```yaml
apiVersion: yiduo.dev/v1alpha1

  name: music-producer-workstation  # 意志决定场景
```

- 配置文件是高维意识的直接投射

## 🎯 关键示例：Wasm 运行时作为后端适配器

```rust
    pub fn run_wasm<P: AsRef<Path>>(&self, wasm_path: P, config: YiduoConfig) -> Result<()> {

        let module = Module::from_file(&self.engine, wasm_path)?;
```

| **配置文件即编程** | 用 YAML 声明式定义"我需要什么" | 用 YAML 声明式选择后端 |
| **关注点分离** | YAML = 声明 / Controller = 执行 | 配置 = 声明 / 调度器 = 执行 |
| **可验证性** | `kubectl apply --dry-run` | `yiduo-device apply --dry-run` |
| **健康检查** | Readiness/Liveness Probes | 后端健康检查与自动修复 |
| **容错机制** | ReplicaSet、自动重启 | 后端 Fallback、降级策略 |

### 借鉴点 1：声明式优先的配置设计

#### K8s 风格的 YAML 配置
```yaml
apiVersion: yiduo.dev/v1alpha1
kind: DeviceSpec
metadata:
  name: smart-camera
  labels:
    device-type: camera
    vendor: sony
    model: imx327

spec:
  # 能力声明（像 K8s 的 Pod 规格）
  capabilities:
    - name: camera
      backend:
        # 主后端
        primary: libcamera
        # 降级选项（像 K8s 的 Pod 反亲和性）
        fallbacks:
          - opencv
          - mock
        # 选择策略
        strategy: prefer-native
        # 健康检查（像 K8s 的 Probes）
        healthCheck:
          enabled: true
          intervalSeconds: 10
          timeoutSeconds: 3
          failureThreshold: 3

    - name: audio
      backend:
        primary: pulseaudio
        fallbacks:
          - alsa
          - mock
        strategy: prefer-compatibility

    - name: display
      backend:
        primary: wayland
        fallbacks:
          - x11
          - mock
        strategy: prefer-performance
```

#### 核心配置字段说明
| 字段 | 说明 | 借鉴来源 |
|------|------|---------|
| `primary` | 首选后端 | K8s 首选调度节点 |
| `fallbacks` | 降级选项 | K8s 节点亲和性降级 |
| `strategy` | 选择策略 | K8s 调度策略 |
| `healthCheck` | 健康检查配置 | K8s Readiness/Liveness |

### 借鉴点 2：关注点分离

#### 架构分层（像 K8s 的分层）
```
┌─────────────────────────────────────────────────────────┐
│  用户层：配置文件（YAML声明）              │
│  device-spec.yaml                            │
│  "我需要什么"（what）                       │
└────────────────────┬────────────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────────────┐
│  调度层：后端调度器（Controller）                │
│  解析配置、选择后端、健康检查              │
│  "怎么去做"（how）                           │
└────────────────────┬────────────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────────────┐
│  实现层：后端适配器（实现）               │
│  Libcamera / OpenCV / Mock / ...          │
│  "实际执行"（actual）                       │
└─────────────────────────────────────────────────────────┘
```

### 借鉴点 3：可验证性

#### 像 K8s 一样的命令行工具
```bash
# 1. 验证配置文件（像 kubectl apply --dry-run）
yiduo-device validate device-spec.yaml
# 输出：✓ Configuration is valid

# 2. 试运行（Dry Run）
yiduo-device apply --dry-run device-spec.yaml
# 输出：
#   ✓ Would use libcamera for camera
#   ✓ Would use pulseaudio for audio
#   ✓ Would use wayland for display

# 3. 实际应用配置
yiduo-device apply device-spec.yaml
# 输出：
#   ✓ Applied configuration
#   ✓ Activated libcamera backend for camera
#   ✓ Activated pulseaudio backend for audio
#   ✓ Activated wayland backend for display

# 4. 查看状态（像 kubectl get pods）
yiduo-device status
# 输出：
#   CAMERA   libcamera  ✓ Healthy  12s
#   AUDIO    pulseaudio ✓ Healthy  12s
#   DISPLAY  wayland    ✓ Healthy  12s

# 5. 切换后端（像 kubectl scale）
yiduo-device switch camera opencv
# 输出：
#   ✓ Switched camera backend from libcamera to opencv
```

### 借鉴点 4：健康检查与容错机制

#### 后端健康检查（像 K8s Probes）
```yaml
spec:
  capabilities:
    - name: camera
      backend:
        primary: libcamera
        fallbacks: [opencv, mock]
        # 健康检查配置
        healthCheck:
          enabled: true
          # 探测间隔（秒）
          intervalSeconds: 10
          # 超时时间（秒）
          timeoutSeconds: 3
          # 连续失败多少次触发降级
          failureThreshold: 3
          # 恢复阈值
          successThreshold: 2
          # 探测命令
          probe:
            type: exec
            command: ["camera-check"]
```

#### 容错机制
```yaml
spec:
  capabilities:
    - name: camera
      implementation:
        primary: libcamera
        fallbacks: [opencv, mock]
        # 容错策略
        faultTolerance:
          # 自动降级
          autoFallback: true
          # 自动恢复
          autoRecovery: true
          # 恢复等待时间（秒）
          recoveryDelaySeconds: 60
```

### 借鉴点 5：配置验证与 Schema

#### 配置 Schema（像 K8s CRD Schema）
```yaml
# 配置文件的类型定义（像 K8s 的 OpenAPI Schema）
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: devicespecs.yiduo.dev
spec:
  group: yiduo.dev
  names:
    kind: DeviceSpec
  versions:
    - name: v1alpha1
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                capabilities:
                  type: array
                  items:
                    type: object
                    properties:
                      name:
                        type: string
                      backend:
                        type: object
                        properties:
                          primary:
                            type: string
                          fallbacks:
                            type: array
                            items:
                              type: string
```

## 实际目录结构与文件组织

### 完整的目录布局

一多 OS 的代码组织采用**功能导向**的目录结构，以"组件"为中心：

```
yiduo/
├── interfaces/                      # WIT 接口定义（组件之间的契约）
│   ├── base/
│   ├── env/
│   └── cap/
│       ├── camera/
│       ├── audio/
│       └── ...
├── runtime/                         # 运行时引擎
│   ├── scheduler/                   # 调度逻辑
│   ├── component_manager/           # 组件加载与管理
│   ├── implementation_manager/      # 实现（后端）管理
│   └── ...
├── implementations/                 # 组件的实现（原 adapters）
│   ├── camera/
│   │   ├── mock/
│   │   ├── libcamera/
│   │   └── opencv/
│   ├── audio/
│   └── ...
├── builtin_components/              # 内置 Wasm 组件
│   ├── camera_component.wasm
│   ├── audio_component.wasm
│   └── ...
├── components/                      # 组件配置（原 scenarios）
│   ├── smart-camera.yaml            # 智能相机组件
│   ├── music-producer.yaml         # 音乐制作人工作站组件
│   └── ...
├── configs/                         # 系统级配置
│   ├── tech-stacks/                 # 技术栈配置（实现选择列表、默认策略）
│   ├── system/                      # 系统级默认配置
│   └── templates/                   # 组件模板（供用户参考和定制）
├── examples/                        # 示例应用
│   ├── hello/                       # 基础 Hello World
│   ├── smart-camera/                # 智能相机场景完整示例
│   ├── custom-component/            # 如何编写自定义组件的示例
│   └── ...
└── docs/                            # 文档
```

### 目录职责详细说明

#### interfaces/ - 标准接口定义
- 所有组件的 WIT 接口定义
- 是整个系统的"契约"和标准

#### runtime/ - 核心运行时引擎
- **scheduler/**: 调度逻辑、策略引擎、健康监控
- **component_manager/**: 负责加载和管理组件（无论是内置还是外部）
- **implementation_manager/**: 管理和协调实现（原 backend_manager）

#### implementations/ - 组件的实现（原 adapters）
- 各种能力的实现
- 每个能力有多个可选实现

#### builtin_components/ - 内置组件
- 预编译的 Wasm 组件模块
- 提供开箱即用的功能
- 由 runtime/component_manager/ 加载和管理

#### components/ vs configs/ - 配置的区别

| 项目 | components/ | configs/ |
|------|-----------|---------|
| **用途** | 用户组件配置 | 系统级配置和模板 |
| **内容** | 用户实际使用的组件 | 技术栈默认值、组件模板 |
| **修改者** | 终端用户 | 系统开发者/高级用户 |
| **例子** | `my-home-surveillance.yaml` | `tech-stacks/camera.yaml`, `templates/music-producer.yaml` |

#### examples/ - 示例和学习资源
- **hello/**: 最简可用示例
- **smart-camera/**: 完整场景示例
- **custom-component/**: 如何开发自定义组件
- 更多实用示例...

### 概念与实现的对应关系

| 概念 | 主要对应的目录 | 说明 |
|------|--------------|------|
| 组件 | `components/` + `builtin_components/` | 用户配置 + 内置实现 |
| 调度整合 | `runtime/scheduler/` | 核心调度逻辑 |
| 接口 | `interfaces/cap/` | 组件之间的契约 |
| 实现 | `implementations/` | 各种能力的实现 |

**重要提示**：四层概念体系是帮助理解的**逻辑模型**，不是严格的代码包划分。一个代码模块可能参与多个概念层！

## 为什么这样设计是正确的？

### 1. 站在巨人肩膀上
- K8s/Docker Compose 已经验证了这套模式的成功
- 开发者已经熟悉这种工作流
- 可以复用很多工具链的设计思想

### 2. 用户体验一致性
- 熟悉 `kubectl` 的开发者可以快速上手
- YAML 配置符合云原生时代的习惯
- 声明式思维已经被广泛接受

### 3. 可扩展性
- 这套模式已经在大规模生产环境中验证
- 可以支持复杂的调度策略和容错机制
- 可以支持多设备、分布式场景

### 4. 清晰的职责边界
- interfaces/ 定义契约，稳定不变
- adapters/ 负责实现，可以灵活替换
- scenarios/ 用户视角，简单易用
- runtime/ 核心引擎，内部实现
