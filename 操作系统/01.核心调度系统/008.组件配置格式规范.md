## 概述

本文档定义一多 OS 组件系统的配置格式规范。

### 🎯 核心理念：一多 OS = Wasm 标准 + 系统级扩展

一多 OS 配置系统**完全建立在 Wasm 生态标准之上，不重复造轮子，只做有价值的系统级扩展**：

| 层次 | Wasm 标准 | 一多 OS 扩展 | 说明 |
|------|----------|-----------|------|
| **接口定义** | ✅ WIT | - | 直接使用官方 WIT |
| **组件组合** | ✅ Wasm Component Model | - | 直接使用官方规范 |
| **多实现选择** | ❌ | ✅ `implementations` + `default-strategy` | 一多 OS 特有 |
| **降级策略** | ❌ | ✅ `fallbacks` | 一多 OS 特有 |
| **场景预设** | ❌ | ✅ `scene-presets` | 一多 OS 特有 |
| **权限声明** | ❌ | ✅ `permissions` | 一多 OS 特有 |
| **健康检查** | ❌ | ✅ （待实现） | 一多 OS 特有 |

### 💡 设计来源：多层借鉴

这个配置系统是**多层借鉴**的结果，按重要性排序：

| 重要性         | 来源                                    | 核心借鉴          |
| ----------- | ------------------------------------- | ------------- |
| 🌟 **主要基础** | **WebAssembly Component Model (WIT)** | 组件接口定义、类型系统   |
| 📱 **概念借鉴** | Android Manifest                      | 声明式清单文件的概念    |
| ☸️ **格式借鉴** | Kubernetes                            | YAML 配置作为单源真理 |
| 📋 **契约借鉴** | OpenAPI/Swagger                       | 人类可读的 API 描述  |

**核心原则**：
- ✅ **WIT 是基石**：优先使用官方的 WebAssembly Component Model 和 WIT 接口定义
- ✅ **声明式清单**：借鉴 Android Manifest 的"我是谁、我能做什么、我需要什么"的声明方式
- ✅ **YAML 配置**：借鉴 Kubernetes 的 YAML 格式，作为人类和机器都能理解的单源真理
- ✅ **只做有价值的扩展**：在标准之上只添加系统级的高级能力（多实现、降级、场景等）

## 核心设计原则

1. **自包含**：组件定义 = 接口 + 依赖 + 实现 + 策略，一个文件搞定
2. **默认优先**：组件内置默认策略，用户只需覆盖差异
3. **场景预设**：提供多种场景的预配置
4. **递归支持**：组件可以嵌套依赖，形成树形结构
5. **声明式**：使用 YAML 格式，借鉴 Kubernetes 成熟经验

## 成熟方案借鉴

### 重要澄清：WIT 是基础，不是替代！

**核心原则**：

- 👉 **直接使用官方的 WIT (WebAssembly Interface Type)** 作为组件接口的基础定义
- 👉 YAML 配置中的 `wit-file` 字段指向实际的 WIT 文件
- 👉 YAML 配置作为**更高层次的系统级抽象**，用于声明式组合

### WIT vs. 我们的 YAML 配置

| 层面               | 用途                       | 格式      | 示例               |
| ---------------- | ------------------------ | ------- | ---------------- |
| **WIT（低层次）**     | 定义 Wasm 组件的导入导出（函数签名、类型） | `.wit`  | `audio-play.wit` |
| **YAML 配置（高层次）** | 定义系统级组件的组合、策略、元数据        | `.yaml` | `Component.yaml` |

### 关系图示

```
┌─────────────────────────────────────────────────────────┐
│  YAML 配置 (Component.yaml)                               │
│  ┌───────────────────────────────────────────────────┐  │
│  │ provides:                                         │  │
│  │   - interface: yiduo:cap/audio-play              │  │
│  │     wit-file: "../wit/audio-play.wit"  ← 指向 WIT│  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────┐
│  WIT 文件 (audio-play.wit)                               │
│  ┌───────────────────────────────────────────────────┐  │
│  │ package yiduo:cap;                                │  │
│  │ interface audio-play {                            │  │
│  │   play: func(data: list<u8>) -> result<unit>;   │  │
│  │ }                                                 │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

### 为什么这样分层？

1. **WIT 作为基础**：
   - 官方标准，工具链完善
   - 跨语言互操作性有保证
   - 适合定义 Wasm 边界的函数签名
2. **YAML 配置作为上层**：
   - 人类友好的声明式配置
   - 包含元数据（名称、版本、描述）
   - 包含策略（实现选择、资源限制）
   - 包含场景预设（不同使用场景的配置）
   - 定义系统级别的组合关系

### io-contracts 的位置

**注意**：文档中的 `io-contracts` 是可选的补充描述，用于：

- 快速参考（不打开 WIT 文件也能理解接口）
- AI 理解（AI 更容易理解 YAML 格式的摘要）
- 但**最终的真理来源是 WIT 文件**

### 推荐的最简配置（不重复定义 io-contracts）

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: audio-processing
spec:
  provides:
    - interface: yiduo:cap/audio-play
      wit-file: "../wit/audio-play.wit"  # 这里定义了 WIT，无需重复
  # 可选：io-contracts 仅用于快速参考
  # io-contracts:
  #   inputs:
  #     - name: data
  #       data-type: list<u8>
  #   outputs:
  #     - name: result
  #       data-type: result<unit>
```

## 为什么 WIT 足够？

WIT 已经提供了完整的类型系统，包括：

- 基本类型：`u8`, `u16`, `u32`, `u64`, `s8`, `s16`, `s32`, `s64`, `f32`, `f64`
- 字符串类型：`string`
- 容器类型：`list<T>`, `option<T>`, `tuple<T1, T2, ...>`
- 记录类型：`record`（类似 struct）
- 变体类型：`variant`（类似 enum 带 payload）
- 结果类型：`result<ok, err>`
- 资源类型：`resource`（用于状态管理）

因此，**我们的设计原则是**：

- ✅ 优先使用 WIT 定义接口
- ✅ YAML 配置用于声明式组合和元数据
- ✅ 避免在 YAML 中重复定义 WIT 已有的内容

## 一多 OS 的 WIT 规范补充

虽然我们使用官方 WIT，但为了确保组件生态的一致性，我们补充以下系统级规范要求：

### 1. 命名约定

#### 包命名规范

```
package yiduo:<category>@<version>;
```

| 部分          | 说明          | 示例                                |
| ----------- | ----------- | --------------------------------- |
| `namespace` | 固定为 `yiduo` | `yiduo`                           |
| `category`  | 功能分类        | `cap` (能力), `sys` (系统), `lib` (库) |
| `version`   | 语义化版本       | `0.1.0`, `1.0.0`                  |

示例：

```wit
package yiduo:cap@0.1.0;  // 能力组件
package yiduo:sys@1.0.0;  // 系统组件
package yiduo:lib@2.0.0;  // 通用库
```

#### 接口命名规范

- 使用 kebab-case（短横线分隔）
- 名称应该清晰描述功能
- 动词 + 名词的组合

```wit
interface audio-play;       // ✅
interface play-audio;       // ✅
interface AudioPlay;        // ❌ 不要使用 PascalCase
interface audio_play;       // ❌ 不要使用下划线
```

#### 世界命名规范

```wit
world <name>-world { ... }
```

示例：

```wit
world audio-processor-world { ... }
world database-world { ... }
```

### 2. 目录结构约定

```
yiduo-package/
├── Component.yaml         # 组件清单配置
├── README.md              # 组件文档
├── wit/                   # WIT 定义目录
│   ├── core.wit           # 核心接口定义
│   └── types.wit          # 共享类型定义
└── impl/                  # 实现目录
    ├── wasm/              # Wasm 实现
    │   └── component.wasm
    └── native/            # 原生实现
        ├── windows.dll
        ├── linux.so
        └── macos.dylib
```

### 3. WIT 文件组织规范

#### 推荐的文件拆分方式

- **types.wit**：共享的类型定义
- **core.wit**：核心接口定义
- 或按功能拆分：**audio.wit**, **video.wit** 等

#### 必须包含的内容

每个 WIT 包应该：

1. 顶部明确声明 package
2. 使用规范的命名
3. 包含必要的文档注释

### 4. 世界定义的标准结构

在一多 OS 中，推荐的 `world` 结构：

```wit
package yiduo:cap@0.1.0;

// 类型定义
interface types {
  record audio-frame {
    channels: u8,
    sample-rate: u32,
    data: list<u8>,
  }
}

// 主接口
interface audio-processor {
  use types.{audio-frame};

  // 处理音频帧
  process: func(frame: audio-frame) -> result<audio-frame, error>;
}

// 标准世界定义
world audio-processor-world {
  // 导入：组件需要从主机获得的能力
  import log: func(msg: string);
  import wasi:filesystem/preopens@0.2.0;

  // 导出：组件提供的能力
  export audio-processor;
}
```

### 5. 文档注释规范

````wit
package yiduo:cap@0.1.0;

/// 音频处理接口
/// 
/// # 功能说明
/// 提供音频数据的处理功能，包括：
/// - 格式转换
/// - 音量调节
/// - 效果处理
///
/// # 示例
/// ```
/// let frame = audio-frame { ... };
/// let result = audio-processor.process(frame);
/// ```
interface audio-processor {
  /// 处理音频帧
  /// @param frame 输入的音频帧
  /// @return 处理后的音频帧
  process: func(frame: audio-frame) -> result<audio-frame, error>;
}
````

### 6. YAML 配置与 WIT 的对应关系

```yaml
# Component.yaml
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: audio-processor
  namespace: yiduo.cap
  version: "1.0.0"
spec:
  provides:
    - interface: yiduo:cap/audio-processor
      # 直接对应 WIT 中的 interface 名称
      wit-file: "./wit/audio-processor.wit"
  requires:
    - name: log
      interface: yiduo:sys/log
      # 直接对应 WIT world 中的 import
      wit-file: "./wit/log.wit"
```

### 7. 版本兼容性规范

遵循语义化版本规范：

- **主版本（MAJOR）**：不兼容的 API 修改
- **次版本（MINOR）**：向下兼容的功能性新增
- **修订版本（PATCH）**：向下兼容的问题修正

### 8. 测试用例约定

推荐在 WIT 文件旁边提供测试契约：

```
wit/
├── audio-processor.wit
└── tests/
    └── audio-processor-test.wit
```

## 总结：完整的规范体系

| 层面     | 标准/规范          | 用途             |
| ------ | -------------- | -------------- |
| **底层** | 官方 WIT 标准      | 接口定义、类型系统      |
| **中层** | 一多 OS WIT 补充规范 | 命名约定、目录结构、世界定义 |
| **上层** | YAML 配置规范      | 组件组合、元数据、策略    |

这样既站在巨人肩膀上（复用官方 WIT），又有我们自己的规范，保证生态一致性！

### 1. Component（组件定义）

这是最核心的配置文件，定义一个完整的组件。

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: audio-processing
  namespace: yiduo.cap
  version: "1.0.0"
  description: "音频处理组件"
  author: "Yiduo Team"
  license: "MIT"

spec:
  # 1. 提供的接口
  provides:
    - interface: yiduo:cap/audio-play
      wit-file: "../wit/audio-play.wit"
    - interface: yiduo:cap/audio-record
      wit-file: "../wit/audio-record.wit"
  
  # 2. 需要的权限（类似 Android 的 <uses-permission>）
  permissions:
    - name: audio.record
      description: "访问麦克风录音"
      required: false
    - name: audio.playback
      description: "播放音频"
      required: true
    - name: storage.read
      description: "读取文件系统"
      required: false
    - name: network.internet
      description: "访问互联网"
      required: false
  
  # 3. 需要的依赖（支持递归）
  requires:
    - name: cpu
      interface: yiduo:base/cpu
      required: true
      version: ">=1.0.0"
    - name: memory
      interface: yiduo:base/memory
      required: true
    - name: optional-feature
      interface: yiduo:cap/optional
      required: false
    - name: camera
      interface: yiduo:cap/camera
      required: false  # ✅ 摄像头是可选的，不是所有系统都需要
      description: "仅在需要摄像功能的场景中使用"
  
  # 3. 输入输出契约（数据流类型约束）
  io-contracts:
    # 输入定义：组件接收什么
    inputs:
      - name: audio-in
        description: "原始音频数据流"
        data-type: yiduo:types/audio-pcm
        sample-rate: 48000
        channels: 2
        required: true
      
      - name: control-commands
        description: "控制命令（音量调节等）"
        data-type: yiduo:types/audio-commands
        required: false
    
    # 输出定义：组件产生什么
    outputs:
      - name: audio-out
        description: "处理后的音频流"
        data-type: yiduo:types/audio-pcm
        sample-rate: 48000
        channels: 2
    
      - name: level-meter
        description: "音频电平计量"
        data-type: yiduo:types/audio-level
        required: false
  
  # 4. 配置参数 Schema
  config:
    $schema: "http://json-schema.org/draft-07/schema#"
    type: object
    properties:
      sample-rate:
        type: integer
        enum: [44100, 48000, 96000]
        default: 48000
      buffer-size:
        type: integer
        default: 1024
        minimum: 64
        maximum: 8192
  
  # 4. 可用实现（自包含，替代原来的 TechStack）
  implementations:
    # 实现1：PortAudio Pro（Wasm 实现，默认）
    - name: portaudio-pro
      description: "专业 PortAudio 实现"
      type: wasm
      platforms: [linux, windows, macos]
      default: true
      wasm-module: "./impl/portaudio-pro.wasm"
      metadata:
        performance: 90
        latency: low
        compatibility: high
      config-defaults:
        portaudio-device: "default"
    
    # 实现2：PortAudio Native（原生实现）
    - name: portaudio-native
      description: "PortAudio 原生高性能实现"
      type: native
      platforms: [linux, windows, macos]
      native-library: "./impl/libportaudio.so"
      native-library-windows: "./impl/portaudio.dll"
      native-library-macos: "./impl/libportaudio.dylib"
      metadata:
        performance: 98
        latency: very-low
        compatibility: medium
    
    # 实现3：JACK
    - name: jack
      description: "JACK Audio Connection Kit"
      type: wasm
      platforms: [linux, macos]
      wasm-module: "./impl/jack.wasm"
      metadata:
        performance: 95
        latency: very-low
    
    # 实现4：ALSA（原生实现）
    - name: alsa-native
      description: "ALSA 原生实现"
      type: native
      platforms: [linux]
      native-library: "./impl/libalsa_wrapper.so"
    
    # 实现5：Mock（测试用）
    - name: mock
      description: "模拟实现（用于测试）"
      type: wasm
      platforms: [all]
      test-only: true
      wasm-module: "./impl/mock.wasm"
  
  # 5. 默认选择策略
  default-strategy:
    preferred: portaudio-pro
    fallbacks: [jack, alsa, mock]
    policy: prefer-low-latency  # 可选: prefer-performance / prefer-compatibility
  
  # 6. 场景预设（可选）
  scene-presets:
    music-production:
      preferred: jack
      fallbacks: [portaudio-pro, alsa]
      config-override:
        sample-rate: 48000
        buffer-size: 64
    
    iot-edge:
      preferred: alsa
      fallbacks: [mock]
      config-override:
        sample-rate: 44100
        buffer-size: 2048
    
    gaming:
      preferred: portaudio-pro
      config-override:
        buffer-size: 256

### 两种接入方式：Wasm vs Native

一多 OS 支持两种组件接入方式，根据性能和兼容性需求选择：

| 特性        | Wasm 实现               | Native 实现                     |
| --------- | --------------------- | ----------------------------- |
| **类型标识**  | `type: wasm`          | `type: native`                |
| **文件格式**  | `.wasm` 模块            | 平台特定库 (`.so`/`.dll`/`.dylib`) |
| **加载方式**  | ⭐⭐⭐⭐⭐ 动态加载            | ⭐⭐⭐⭐⭐ 动态加载                    |
| **安全性**   | ⭐⭐⭐⭐⭐ 沙箱隔离            | ⭐⭐ 直接访问系统                     |
| **跨平台配置** | ⭐⭐⭐⭐⭐ 一个 Wasm 文件全平台通用 | ⭐⭐⭐⭐⭐ 一套配置支持多平台（自动选择库文件）      |
| **性能**    | ⭐⭐⭐⭐ 接近原生             | ⭐⭐⭐⭐⭐ 最高性能                    |
| **部署包大小** | ⭐⭐⭐⭐⭐ 单文件，体积小         | ⭐⭐⭐ 需包含多平台库，体积较大              |
| **延迟**    | ⭐⭐⭐ 中等                | ⭐⭐⭐⭐⭐ 最低                      |

#### 1. Wasm 实现（推荐用于大多数场景）

```yaml
- name: portaudio-pro
  type: wasm
  wasm-module: "./impl/portaudio-pro.wasm"
```

**适用场景**：

- ✅ 跨平台应用
- ✅ 需要隔离的第三方组件
- ✅ 对性能要求不是极端苛刻
- ✅ 快速原型开发

#### 2. Native 实现（推荐用于高性能场景）

```yaml
- name: portaudio-native
  type: native
  # 通用路径（Linux 默认）
  native-library: "./impl/libportaudio.so"
  # 平台特定路径（可选）
  native-library-windows: "./impl/portaudio.dll"
  native-library-macos: "./impl/libportaudio.dylib"
```

**适用场景**：

- ✅ 极致性能需求（音频、视频、游戏）
- ✅ 需要直接硬件访问
- ✅ 特定平台优化
- ✅ 已有原生库需要集成

#### 3. 配置字段详细说明

| 字段                       | 是否必填        | 说明                     | 示例                      |
| ------------------------ | ----------- | ---------------------- | ----------------------- |
| `type`                   | ✅ 必需        | 实现类型：`wasm` 或 `native` | `type: wasm`            |
| `wasm-module`            | `wasm` 必需   | Wasm 模块路径              | `"./impl/xxx.wasm"`     |
| `native-library`         | `native` 必需 | 原生库通用路径                | `"./impl/libxxx.so"`    |
| `native-library-windows` | 可选          | Windows 特定路径           | `"./impl/xxx.dll"`      |
| `native-library-macos`   | 可选          | macOS 特定路径             | `"./impl/libxxx.dylib"` |

    - name: storage.read
      description: "读取文件系统"
      required: true
    - name: storage.write
      description: "写入文件系统"

      description: "数据库网络通信"
      required: false

    - name: storage
      interface: yiduo:cap/storage
      wit-file: "../wit/storage.wit"
      required: true
  
  # 4. 配置参数 Schema
  config:
    properties:
      connection-pool:
        type: integer
        default: 10
        minimum: 1
        maximum: 100

      wasm-module: "./impl/sqlite-wasm.wasm"
      metadata:
        performance: 70
        compatibility: 100
    
    - name: postgres-native
      type: native
      platforms: [linux, macos]
      native-library: "./impl/libpq.so"
      metadata:
        performance: 95
        compatibility: 60
```

**对应的 WIT 文件（database-query.wit）：**

```wit
package yiduo:cap@0.1.0;

// 类型定义
interface types {
  // SQL 查询类型
  type sql-query = string;
  
  // SQL 参数类型
  record sql-param {
    name: string,
    value: string,
  }
  type sql-params = list<sql-param>;
  
  // 查询结果集
  record sql-resultset {
    columns: list<string>,
    rows: list<list<string>>,
  }
}

// 数据库查询接口
interface database-query {
  use types.{sql-query, sql-params, sql-resultset};
  
  /// 执行 SQL 查询
  /// @param query SQL 查询语句
  /// @param params 可选参数绑定
  /// @return 查询结果
  execute: func(
    query: sql-query,
    params: option<sql-params>,
  ) -> result<sql-resultset, string>;
}

// 世界定义
world database-world {
  import wasi:filesystem/preopens@0.2.0;
  export database-query;
}
```

**工作原理示例：**

1. **输入**：接收 `"SELECT * FROM products WHERE price < 100"`
2. **处理**：通过 `sqlite-wasm` 或 `postgres-native` 实现执行查询
3. **输出**：返回结构化的 `sql-resultset`，包含匹配的产品数据

## 权限系统设计

### 为什么需要权限系统？

虽然 Wasm 提供了沙箱隔离，但我们仍然需要类似 Android 的权限系统，原因：

| 原因         | 说明                   |
| ---------- | -------------------- |
| **声明式声明**  | 组件需要明确声明"我需要访问什么能力"  |
| **用户知情同意** | 用户需要知道并同意组件能访问什么     |
| **细粒度控制**  | 系统需要进行细粒度控制，而不是全有或全无 |
| **安全审计**   | 可以审计组件的权限使用情况        |

### 权限分类

#### 1. 能力权限（Capabilities）

对应组件需要访问的硬件/系统能力：

| 权限               | 说明        | 示例      |
| ---------------- | --------- | ------- |
| `camera.access`  | 访问摄像头     | 拍照、视频录制 |
| `audio.record`   | 访问麦克风     | 录音      |
| `audio.playback` | 播放音频      | 音乐播放    |
| `location.gps`   | 访问 GPS 位置 | 定位服务    |
| `bluetooth`      | 访问蓝牙      | 设备连接    |
| `usb.host`       | 访问 USB 主机 | 外设连接    |

#### 2. 存储权限（Storage）

对文件系统的访问权限：

| 权限                | 说明       |
| ----------------- | -------- |
| `storage.read`    | 读取文件系统   |
| `storage.write`   | 写入文件系统   |
| `storage.private` | 访问组件私有存储 |
| `storage.shared`  | 访问共享存储   |

#### 3. 网络权限（Network）

网络访问权限：

| 权限                 | 说明        |
| ------------------ | --------- |
| `network.internet` | 访问互联网     |
| `network.local`    | 访问本地网络    |
| `network.server`   | 作为服务器监听端口 |

#### 4. 系统权限（System）

系统级别的权限：

| 权限                    | 说明     |
| --------------------- | ------ |
| `system.settings`     | 修改系统设置 |
| `system.notification` | 发送通知   |
| `system.power`        | 电源管理   |
| `system.process`      | 管理进程   |

### 权限配置格式

```yaml
spec:
  permissions:
    # 方式1：简单声明
    - name: audio.playback
      required: true
    
    # 方式2：详细声明
    - name: camera.access
      required: false
      description: "仅在需要拍照功能时使用"
      reason: "用户头像拍摄"
    
    # 方式3：带条件的权限
    - name: network.internet
      required: false
      when: "config.enable-online-features == true"
      description: "仅在启用在线功能时需要"
```

### 权限运行时流程

```
┌─────────────────────────────────────────────────┐
│ 1. 组件声明权限（Component.yaml）                 │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│ 2. 系统验证权限完整性                            │
│    - 检查是否所有 required 权限都被同意           │
│    - 检查权限是否有效                            │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│ 3. 用户授权（首次使用或配置）                     │
│    - 类似 Android 的运行时权限请求                │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│ 4. Wasm 沙箱 + 权限拦截                          │
│    - Wasm 沙箱提供隔离                           │
│    - 权限系统在 WASI 层进行拦截                   │
│    - 只有被授权的权限才能通过                     │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│ 5. 权限审计（可选）                              │
│    - 记录权限使用情况                            │
│    - 异常检测                                    │
└─────────────────────────────────────────────────┘
```

### 与 Wasm/WASI 的关系

| 层次             | 职责                   |
| -------------- | -------------------- |
| **Wasm 沙箱**    | 提供基础隔离，确保代码不能直接访问宿主机 |
| **WASI 接口**    | 提供标准化的系统访问接口         |
| **一多 OS 权限系统** | 在 WASI 之上进行细粒度权限控制   |
| **配置文件声明**     | 提前声明需要什么权限，让用户知情     |

**类比**：

- Wasm 沙箱 = 公寓的大门
- WASI 接口 = 公寓内的设施接口
- 一多 OS 权限系统 = 每个房间的门锁
- 配置文件声明 = 提前告诉用户"我需要进哪些房间"

### 组件交互的最佳实践

上面我们讨论了**配置层面的循环依赖**（`requires` 形成的循环），但还有**运行时交互层面**的设计需要注意。

***

### 避免循环依赖的三种架构模式

#### 1. 事件驱动架构（推荐）

**设计理念**：组件之间通过事件总线通信，不直接依赖对方。

```
┌─────────────────────────────────────────────────────────────┐
│                   Event Bus (事件总线)                      │
└─────────────────────────────────────────────────────────────┘
            ↑                     ↓                    ↑
    ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
    │ Component A   │   │ Component B   │   │ Component C   │
    │ (Publishes)   │   │  (Listens)    │   │  (Listens)    │
    └───────────────┘   └───────────────┘   └───────────────┘
```

**WIT 定义示例**：

```wit
package yiduo:events@0.1.0;

interface event-bus {
  // 发布事件
  publish: func(event: event) -> result<unit, string>;
  
  // 订阅事件
  subscribe: func(event-type: string, callback: func(event: event)) -> result<subscription-id, string>;
  
  // 取消订阅
  unsubscribe: func(sub-id: subscription-id) -> result<unit, string>;
}

// 事件类型
record event {
  type: string,
  payload: string,
  timestamp: u64,
}
type subscription-id = string;
```

**优点**：

- ✅ 完全解耦，组件之间没有直接依赖
- ✅ 天然支持广播模式
- ✅ 容易扩展和调试

***

#### 2. 中间件协调模式

**设计理念**：引入一个协调器（Coordinator）来处理复杂交互。

```
              ┌───────────────┐
              │ Coordinator   │
              │  (中间件)     │
              └──────┬───────┘
                    │
         ┌──────────┼──────────┐
         ↓          ↓          ↓
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ Component│ │ Component│ │ Component│
   │    A     │ │    B     │ │    C     │
   └──────────┘ └──────────┘ └──────────┘
```

**YAML 配置示例**：

```yaml
# Coordinator 组件
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: workflow-coordinator
spec:
  requires:
    - name: component-a
      interface: yiduo:cap/service-a
    - name: component-b
      interface: yiduo:cap/service-b
    - name: component-c
      interface: yiduo:cap/service-c
```

**优点**：

- ✅ 业务逻辑集中在 Coordinator
- ✅ 组件之间互不认识
- ✅ 工作流变更只需修改 Coordinator

***

#### 3. 单向依赖层（分层架构）

**设计理念**：严格分层，每一层只依赖更底层。

```
Layer 3 (应用层)
    ↓ 依赖
Layer 2 (服务层)
    ↓ 依赖
Layer 1 (基础设施层)
```

**示例**：

- Layer 1: 文件系统、网络等基础能力
- Layer 2: 数据库、缓存等通用服务
- Layer 3: UI、业务逻辑等应用组件

**优点**：

- ✅ 结构清晰，理解容易
- ✅ 不会有跨层的循环依赖
- ✅ 符合经典架构最佳实践

***

### 常见反模式与避免方案

| 反模式             | 问题    | 解决方案                  |
| --------------- | ----- | --------------------- |
| **组件 A ↔ 组件 B** | 双向依赖  | 使用事件总线或引入 Coordinator |
| **组件知道太多**      | 紧耦合   | 定义最小的接口，只暴露必要的功能      |
| **巨型组件**        | 难以维护  | 按职责拆分为多个小组件           |
| **数据传递不规范**     | 类型不安全 | 使用 WIT 定义的强类型接口       |

***

### 实际场景示例：音乐播放器

**不好的设计**（紧耦合）：

```
音频解码器 ←→ 播放器 ←→ UI 组件
```

**好的设计**（事件驱动）：

```
事件总线:
  - audio-frame-ready
  - playback-state-changed
  - user-command

组件:
  1. 解码器 → 发布 audio-frame-ready
  2. 播放器 → 监听 audio-frame-ready，发布 playback-state-changed
  3. UI → 监听 playback-state-changed，发布 user-command
```

这样每个组件都独立进化，互不干扰！

## ⚡ 增量验证：只验证变更的组件

### 核心思想

**只重新验证变更的文件！**

### 为什么需要增量验证？

| 场景              | 全量验证   | 增量验证  | 提升      |
| --------------- | ------ | ----- | ------- |
| 单文件变更 (1000 组件) | 1000 次 | 1 次   | 1000x ⚡ |
| 小部分变更 (1%)      | 1000 次 | 10 次  | 100x    |
| 大规模变更 (50%)     | 1000 次 | 500 次 | 2x      |

### 最简单的实现方案

不需要复杂的依赖分析，只需要：

1. **缓存验证结果**
   - 记录每个文件的验证结果
   - 记录文件的修改时间
2. **检查是否需要重新验证**
   ```
   当验证文件时:
     if (文件当前修改时间 > 缓存记录的修改时间):
         重新验证
         更新缓存
     else:
         直接用缓存结果
   ```

### 数据结构

```
缓存条目: {
  文件路径: String
  文件修改时间: Int64  // 时间戳
  验证结果: Bool
  验证时间: Int64
}

验证器: {
  缓存: Map<文件名 -> 缓存条目>
}
```

### 工作流程

```
第一轮验证:
  [验证] audio.yaml  ← 第一次验证
  [验证] camera.yaml ← 第一次验证

第二轮验证 (相同文件):
  [缓存命中] audio.yaml  ← 没变，用缓存
  [缓存命中] camera.yaml ← 没变，用缓存

第三轮验证 (audio.yaml 变更):
  [验证] audio.yaml  ← 变了，重新验证
  [缓存命中] camera.yaml ← 没变，用缓存
```

### 与四元架构的关系

| 四元架构         | 验证系统对应      |
| ------------ | ----------- |
| 💭 配置文件 = 意志 | 验证的输入       |
| 🧬 器官 = DNA  | 验证的对象       |
| 🌳 树形 = 生长路径 | (高级功能，暂不需要) |

基于基础配置骨架，以下 5 个进阶特性让组件从"能用"升级到"好用"、"智能"，真正达到数字生命体的水准。

### 🧬 1. 特性开关（Feature Gates）与条件加载

让组件具备更强的环境感知能力，避免无效加载和启动报错。

```yaml
spec:
  implementations:
    # GPU 加速实现：只有检测到 CUDA 且用户开启高性能模式时才加载
    - name: gpu-acceleration
      type: native
      # ✅ 条件判断：只有满足这些条件才加载此实现
      if: "system.has_cuda == true && config.performance-mode == 'high'"
      native-library: "./impl/libcuda_wrapper.so"
      metadata:
        performance: 98
    
    # 软件降级实现：始终可用
    - name: software-render
      type: wasm
      default: true
      wasm-module: "./impl/software.wasm"
```

**条件表达式语法**（简化版）：

- `system.has_cuda` - 系统功能检测
- `config.performance-mode` - 用户配置
- `platform.os == 'linux'` - 平台判断
- 逻辑运算：`&&`、`||`、`!`

### ⚡ 2. 热更新与版本灰度策略

赋予系统"新陈代谢"的能力，保证升级时不会"休克"。

```yaml
spec:
  components:
    - name: audio-core
      type: yiduo.cap/audio-processing:1.0.0
      
      # ✅ 热更新策略
      update-strategy:
        policy: "RollingUpdate"  # 滚动更新
        max-unavailable: 1        # 最多允许1个实例不可用
        canary-percentage: 10     # 金丝雀发布比例（先给10%用户用）
        auto-rollback: true       # 出错自动回滚
```

**策略类型**：

- `RollingUpdate` - 滚动更新（推荐）
- `Recreate` - 先停后起（不推荐）
- `BlueGreen` - 蓝绿部署（适用于关键组件）

### 🔗 3. 数据流类型约束（Data Contracts）

给血液系统（链式架构）增加"血型检测"，防止排异反应。

```yaml
spec:
  # 组件间连接定义
  connections:
    - from: camera.output
      to: ai-detector.input
      
      # ✅ 强制数据格式与校验
      transform: "raw-frame-to-tensor"  # 数据转换方式
      data-contract:
        input-type: "yiduo:types/video-raw"
        output-type: "yiduo:types/tensor-float32"
        validate-checksum: true  # 校验数据完整性
```

**价值**：

- A 输出 PCM，B 期待 MP3 → 配置时就报错，而不是运行时崩溃
- 显式声明数据契约，让数据流可追溯

### 🔋 5. 资源配额与熔断机制（QoS & Circuit Breaker）

数字生命体的"免疫系统"，防止"癌变"组件拖垮整个机体。

```yaml
spec:
  # ✅ 资源配额
  resources:
    requests:
      memory: "64Mi"      # 最小内存需求
      cpu-percent: 5      # 最小 CPU 需求
    limits:
      memory: "128Mi"     # 最大内存限制
      cpu-percent: 15     # 最大 CPU 限制
      network-bandwidth: "1Mbps"
  
  # ✅ 熔断与恢复机制
  resilience:
    restart-policy: "Always"  # 崩溃后自动重启
    max-restarts: 3           # 最多重启 3 次
    circuit-breaker:
      enabled: true
      failure-threshold: 5     # 连续失败 5 次后自动熔断
      recovery-time: "30s"    # 30秒后尝试恢复
      timeout: "5s"           # 单次调用超时
```

**工作原理**：

1. 组件连续失败 5 次 → 熔断（隔离此组件）
2. 等待 30 秒 → 半开状态（允许少量流量测试）
3. 测试成功 → 恢复正常
4. 测试失败 → 继续熔断

## 与 001 设计原则的对应关系

本规范完全符合 [001.设计原则](file:///d:\yiduo\interfaces\技术文档\001.设计原则：如何做到足够优雅、足够抽象.md) 中的三大核心原则：

### 1. 🔗 链式架构（血液系统）- 根本

| 配置规范特性                  | 对应设计原则        |
| ----------------------- | ------------- |
| WIT 接口定义                | 链式骨架，稳定不变     |

### 2. 🌳 树形架构（生长的器官）- 应变

| 配置规范特性                 | 对应设计原则    |
| ---------------------- | --------- |
| 多实现选择（implementations） | 在链节点上灵活生长 |
| 场景预设（scene-presets）    | 不同器官组合方式  |
| 递归依赖                   | 树状结构，枝繁叶茂 |

### 3. 📋 配置文件即编程（DNA）- 蓝图

| 配置规范特性           | 对应设计原则          |
| ---------------- | --------------- |
| 声明式 YAML 配置      | DNA 蓝图，定义"需要什么" |
| Application 组合配置 | 灵活组合，像编程一样表达需求  |
| 递归验证             | DNA 检测，验证正确性    |

### 三大设计原则的体现

| 原则       | 体现                |
| -------- | ----------------- |
| **简单性**  | 组件小而专一，拆成独立积木     |
| **正交性**  | 组件之间独立，通过接口契约连接   |
| **可组合性** | 配置文件自由组合，解决任意业务需求 |

### 为什么移除"组件继承（extends）"？

设计原则明确指出：**组合优先而非继承**（001 文档第 676 行）。继承会：

- ❌ 破坏简单性：组件变得复杂
- ❌ 破坏正交性：组件之间产生耦合
- ❌ 违背树形架构：继承链可能混乱

✅ **替代方案**：用组件组合（ComponentTemplate）和配置覆盖来实现类似效果

## 📱 与 Android 应用清单的对比

### 核心理念一致性

就像 Android 应用必须包含 `AndroidManifest.xml` 一样，一多 OS 的每个组件都必须包含 `Component.yaml`：

| 方面       | Android               | 一多 OS            |
| -------- | --------------------- | ---------------- |
| **清单文件** | `AndroidManifest.xml` | `Component.yaml` |
| **声明式**  | XML 声明应用信息            | YAML 声明组件信息      |
| **作用**   | 定义应用身份、能力、需求          | 定义组件身份、能力、需求     |

### 详细对比表

#### 1. 基本信息

| AndroidManifest.xml                    | Component.yaml          | 说明      |
| -------------------------------------- | ----------------------- | ------- |
| `<manifest package="com.example.app">` | `namespace: yiduo.cap`  | 包名/命名空间 |
| `android:versionName="1.0.0"`          | `version: "1.0.0"`      | 版本号     |
| `android:label="@string/app_name"`     | `description: "音频处理组件"` | 名称/描述   |

#### 2. 提供的能力

| AndroidManifest.xml                       | Component.yaml                        | 说明          |
| ----------------------------------------- | ------------------------------------- | ----------- |
| `<activity android:name=".MainActivity">` | `provides:`                           | 提供的界面/能力    |
| `<service android:name=".PlayerService">` | `- interface: yiduo:cap/audio-play`   | 提供的服务/接口    |
| `<receiver android:name=".Receiver">`     | `- interface: yiduo:cap/audio-record` | 提供的广播接收器/接口 |
| `<provider android:name=".Provider">`     | (更多接口...)                             | 提供的内容提供器/接口 |

#### 3. 需要的权限

| AndroidManifest.xml                                               | Component.yaml          | 说明     |
| ----------------------------------------------------------------- | ----------------------- | ------ |
| `<uses-permission android:name="CAMERA" />`                       | `permissions:`          | 需要的权限  |
| `<uses-permission android:name="INTERNET" />`                     | `- name: camera.access` | 具体权限声明 |
| `<uses-permission android:name="RECORD_AUDIO" />`                 | `- name: audio.record`  | 具体权限声明 |
| `<uses-feature android:name="camera" android:required="false" />` | `required: false`       | 可选权限声明 |

#### 4. 需要的依赖

| AndroidManifest.xml | Component.yaml   | 说明      |
| ------------------- | ---------------- | ------- |
| (无直接对应)             | `requires:`      | 需要的组件依赖 |
| (通过 Gradle 依赖)      | `- name: cpu`    | 需要的具体组件 |
| (通过 Gradle 依赖)      | `- name: memory` | 需要的具体组件 |

#### 5. 实现选择（一多 OS 特有）

| 一多 OS               | 说明                                           |
| ------------------- | -------------------------------------------- |
| `implementations:`  | 组件可用的实现（类似 Android 的 `minSdkVersion` 适配不同版本） |
| `default-strategy:` | 默认选择策略（类似 Android 的首选配置）                     |
| `scene-presets:`    | 场景预设（类似 Android 的不同配置变体）                     |

### 示例对比

#### AndroidManifest.xml 示例

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.example.musicplayer"
    android:versionName="1.0.0">

    <application
        android:label="音乐播放器"
        android:description="专业的音乐播放应用">

        <!-- 提供的能力 -->
        <activity android:name=".MainActivity" />
        <service android:name=".PlayerService" />

        <!-- 需要的权限 -->
        <uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE" />
        <uses-permission android:name="android.permission.INTERNET" />

        <!-- 需要的硬件特性 -->
        <uses-feature android:name="android.hardware.audio.output" />

    </application>
</manifest>
```

#### Component.yaml 示例（对应）

```yaml
apiVersion: yiduo.dev/v1alpha1
kind: Component
metadata:
  name: music-player
  namespace: com.example
  version: "1.0.0"
  description: "专业的音乐播放组件"

spec:
  # 提供的能力（对应 <activity>, <service>）
  provides:
    - interface: com.example:player/ui
    - interface: com.example:player/playback

  # 需要的依赖（对应 <uses-permission>, <uses-feature>）
  requires:
    - name: storage
      interface: yiduo:storage/filesystem
      required: true
    - name: network
      interface: yiduo:network/http
      required: true
    - name: audio
      interface: yiduo:cap/audio-play
      required: true

  # 配置参数
  config:
    schema:
      type: object
      properties:
        default-volume: { type: float, default: 0.8 }

  # 可用实现（一多 OS 特有）
  implementations:
    - name: gstreamer-player
      default: true
    - name: ffmpeg-player
    - name: mock
      test-only: true

  # 默认策略
  default-strategy:
    preferred: gstreamer-player
    fallbacks: [ffmpeg-player, mock]
```

### 为什么选择 YAML 而不是 XML？

| 方面           | XML（Android） | YAML（一多 OS）                        |
| ------------ | ------------ | ---------------------------------- |
| **可读性**      | 较繁琐，标签嵌套深    | 简洁，层次清晰                            |
| **书写体验**     | 需要闭合标签       | 缩进即可，更快捷                           |
| **生态**       | Android 生态使用 | Kubernetes、Docker Compose 等云原生生态使用 |
| **与 WIT 配合** | 一般           | YAML + WIT 的组合更现代                  |

### 关键差异

| 方面       | Android  | 一多 OS            |
| -------- | -------- | ---------------- |
| **粒度**   | 整个应用一个清单 | 每个组件一个清单         |
| **递归**   | 清单文件不递归  | 组件可以递归依赖其他组件     |
| **多实现**  | 主要是版本适配  | 每个组件可以有多个完全不同的实现 |
| **策略配置** | 通过资源配置适配 | 内置策略配置和场景预设      |

### 总结

**是的！这个配置系统确实类似 Android 应用清单，但更强大！**

- ✅ **灵感相同**：都是声明式的清单文件，定义"我是谁"、"我能做什么"、"我需要什么"
- ✅ **但更强大**：支持递归依赖、多实现选择、策略配置、场景预设
- ✅ **更现代**：使用 YAML，借鉴 Kubernetes 等云原生技术的成熟经验
- ✅ **组件化**：不仅是应用，每个小组件都有自己的清单

## 🎯 总结：一多 OS = Wasm 标准 + 系统级扩展

### 核心立场：不重复造轮子，只做有价值的扩展

| 层次 | Wasm 生态标准 | 一多 OS 系统级扩展 | 说明 |
|------|-------------|----------------|------|
| **接口定义** | ✅ WIT | - | 直接使用官方标准 |
| **组件组合** | ✅ Wasm Component Model | - | 直接使用官方规范 |
| **多实现选择** | ❌ | ✅ `implementations` + `default-strategy` | 系统特有 |
| **降级策略** | ❌ | ✅ `fallbacks` | 系统特有 |
| **场景预设** | ❌ | ✅ `scene-presets` | 系统特有 |
| **权限声明** | ❌ | ✅ `permissions` | 系统特有 |
| **健康检查** | ❌ | ✅ (待实现) | 系统特有 |

### 为什么这样设计？

1. **利用 Wasm 生态：已经成熟，直接用，不重复造轮子**
   - WIT 接口定义已经完善
   - Wasm 组件模型已经标准化
   - 工具链（Wasmtime、WasmEdge 等）已经成熟

2. **系统级能力：才是一多 OS 的价值所在**
   - 多实现选择 + 降级策略：给用户选择权
   - 场景预设：简化常见场景
   - 权限系统：细粒度的安全控制
   - 健康检查：确保系统稳定运行

   - 标准 Wasm 组件可以直接在一多 OS 运行
   - 一多 OS 的组件也可以在标准 Wasm 环境运行
   - 不锁死在单一生态
