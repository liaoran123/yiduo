# 一多OS调度系统开发原则与指南

> **给AI助手的参考文档**：确保下次不会考虑不周

---

## 🎯 一、核心定位

### 1.1 任务聚焦

| 方面 | 当前任务 | 暂时不做 |
|------|---------|---------|
| **核心** | 调度系统 + 性能优化 | 其他功能（如可观测性、安全审计等） |
| **时间点** | MVP阶段 | 未来生态构建 |

### 1.2 核心使命

一多OS**只做一件事，只做好一件事**：

> **调度与整合**，不重复造轮子

---

## 🏗️ 二、架构原则

### 2.1 分层架构：明确边界，不混淆

| 层级 | 内容 | 实现方式 | 性能要求 |
|------|------|---------|---------|
| 🔴 **内联核心** | 调度决策、消息路由、事件总线、缓存层 | Native代码，直接编译 | 极高（微秒/纳秒级） |
| 🟡 **混合层** | 健康检查框架、策略框架 | 框架内联，插件Wasm | 中高 |
| 🟢 **Wasm组件** | AI大脑、能力提供者、业务逻辑 | 标准Wasm组件 | 灵活可扩展 |

### 2.2 内联核心的判定标准

如果满足以下任一条件，应该内联：

1. **热路径**：每个请求都会执行
2. **微秒级延迟要求**
3. **极高频率调用**（>1M次/秒）
4. **组件间消息路由**

### 2.3 元内核是唯一的特殊情况

| 元内核 | 特点 |
|--------|------|
| **唯一硬编码** | 极小（<1000行），不可修改 |
| **职责** | 基础硬件初始化 + 拉起第一个Wasm组件 + 信任验证 |
| **地位** | 系统的信任根，除此之外，一切皆组件 |

## 💡 三、设计原则

### 3.1 调度系统的哲学

> **管血液，不管器官**

- **调度系统负责**：组件间的交互、数据流动、协调调度
- **业务逻辑负责**：器官功能，通过Wasm组件实现
- **不做**：不介入组件内部实现

### 3.2 WIT优先原则

- **WIT是唯一接口标准**：所有组件通过WIT定义契约
- **组件匹配**：WIT匹配即可通讯，不管语言和实现

### 3.3 不重复造轮子

- **复用成熟生态**：wRPC、wasabio、wasm-ripple等项目直接用
- **重点在调度逻辑**：把调度器的"意志"注入到现有基础设施

## 🚀 四、开发优先级

### 4.1 第一优先级

| 任务 | 说明 |
|------|------|
| 基准测试框架 | 量化性能，找到瓶颈 |
| 内联核心优化 | 调度决策、消息路由、事件总线 |
| 文档完善 | 架构说明、使用指南 |

### 4.2 第二优先级（未来）

| 任务 | 说明 |
|------|------|
| Wasm组件功能 | 可观测性、安全审计等 |
| 生态工具链 | 组件组合编译等 |

## 📋 五、AI助手检查清单

每次处理一多OS相关任务，请按顺序检查：

1. **是否混淆了内联核心和Wasm组件边界？**
   - 性能关键 → 内联核心
   - 灵活可扩展 → Wasm组件

2. **是否超出了当前任务范围？**
   - 当前：调度系统 + 性能优化
   - 不做：其他功能

3. **是否考虑了架构重构？**
   - 我们的原则：**不重构**，只优化和完善

4. **是否忘记了"不重复造轮子"原则？**
   - 先查：有没有成熟项目可以复用

5. **是否保持了"一切皆组件"（除元内核）原则？**
