## 🔍 关键概念澄清

### 📌 重要区分："注册" vs "加载" vs "执行"

| 概念 | 含义 | 是否需要 Wasm/.so |
|---|---|---|
| **注册 (Register)** | 在组件表中创建条目，记录信息 | ❌ 不需要 |
| **加载 (Load)** | 真正加载 Wasm/.so 文件到内存 | ✅ 需要 |
| **执行 (Execute)** | 运行组件的代码逻辑 | ✅ 需要 |

- 没有强制要求组件必须是 Wasm/.so

## ✅ 调度核心自注册的设计方案

### 🎯 核心思路

**调度核心不需要加载，因为它已经在运行了！**

它只需要"注册"自己的信息，这样：
1. 其他组件可以通过能力匹配找到它
2. 可以向它发送消息
3. 它可以响应这些消息

---

### 📋 具体设计

在调度器创建时，自动"自注册"：

```moonbit
// 在 create() 函数中
fn create() -> Scheduler {
  let dummy_msg = ...
  let dummy_comp: Option[ComponentInfo] = None
  
  // 1. 创建调度器
  let mut scheduler = Scheduler::{
    high_queue: @core.RingBuffer::create(...),
    normal_queue: @core.RingBuffer::create(...),
    low_queue: @core.RingBuffer::create(...),
    pool: @core.MemoryPool::create(...),
    components: FixedArray::make(32, dummy_comp),
    max_components: 32,
    is_running: false
  }
  
  // 2. 自注册！（关键）
  let self_info = ComponentInfo::{
    name: "scheduler-core",
    component_type: "native-core",  // ⚠️ 特殊类型，标记它是调度核心
    status: Created,
    capabilities: ["scheduling", "component-mgmt", "message-dispatch"]
  }
  
  let (s, self_id) = register(scheduler, self_info)
  s
}
```

---

### 🎯 为什么这样设计是正确的？

#### 1️⃣ 调度核心是"特殊组件"
- 它已经在运行中，不需要加载
- 它的代码是调度器本身的一部分
- 它只需要在组件表中有一个条目

#### 2️⃣ 能力匹配可以正常工作
- 其他组件可以查找具备 "scheduling" 能力的组件
- 它们会找到调度核心（ID: 0）
- 它们可以向调度核心发送消息

#### 3️⃣ 消息分发可以正常工作
- 当消息目标是调度核心（ID: 0）时
- 分发逻辑会识别出来
- 调度核心可以直接处理这些消息（不需要加载）

## 💡 关键设计要点

### 1. component_type 的语义

| component_type | 含义 | 是否需要加载 |

| "wasm" | Wasm 组件 | ✅ 需要加载 Wasm 文件 |

### 🔄 3. 配置文件的作用是什么？

**关键：配置文件只决定"加载哪些组件"，不决定"运行时调用！**

| 阶段 | 配置文件的作用 | 调用的方式 |
|---|---|---|
| **启动时** | 从配置加载组件，注册到组件表 | ❌ 不参与 |
| **运行时** | ❌ 不参与 | 组件通过能力匹配找到对方 |

**运行时调用不依赖配置文件！配置文件只是启动时用一次。**

#### 1️⃣ 引入"零号组件"契约 ⭐⭐⭐⭐⭐ (强烈推荐)

**temp.md 建议**：
> 显式定义 `ComponentID::ZERO` 或 `SCHEDULER_CORE_ID`，将 ID:0 变成系统契约。

**当前代码问题**：
- `dispatch()` 函数中 `if to_id == 0` 是魔法数字
- 缺乏契约化的定义

**最佳实施方案**：

```moonbit
// 在 scheduler.mbt 头部添加
const SCHEDULER_CORE_ID: Int = 0
const COMPONENT_TYPE_NATIVE_CORE: String = "native-core"

// 在 dispatch() 中使用
fn dispatch(self: Scheduler, msg: @core.Message) -> Scheduler {
  let (to_id, need_release) = parse_to_id(msg)
  
  if to_id == SCHEDULER_CORE_ID {  // 使用常量，不是魔法数字
    self.handle_core_message(msg)
  } else {
    // 正常组件处理
  }
}

// 在自注册时使用
let self_info = ComponentInfo::{
  name: "scheduler-core",
  component_type: COMPONENT_TYPE_NATIVE_CORE,  // 统一使用常量
  status: Created,
  capabilities: ["scheduling", "component-mgmt", "message-dispatch"]
}
```

**为什么这样最好**：
- 契约化，无歧义
- 编译期可验证
- 易于理解和维护

**✅ 已在当前代码中实施！**

#### 2️⃣ 完善 component_type 类型安全 ⭐⭐⭐⭐ (推荐)

**temp.md 建议**：
> 将 component_type 从 String 升级为 Enum。

**当前代码问题**：
```moonbit
struct ComponentInfo {
  component_type: String  // 类型不安全，可能拼写错误
}
```

**最佳实施方案（平衡安全与灵活）**：

```moonbit
// 在 scheduler.mbt 中添加
enum ComponentType {
  Wasm
  Native
  NativeCore
  MoonBit
  Custom(String)  // 保留灵活性
}

// 修改 ComponentInfo
struct ComponentInfo {
  name: String
  component_type: ComponentType  // 类型安全的枚举
  status: ComponentStatus
  capabilities: List[String]
}

// 添加辅助函数
fn component_type_to_string(ct: ComponentType) -> String {
  match ct {
    Wasm => "wasm"
    Native => "native"
    NativeCore => "native-core"
    MoonBit => "moonbit"
    Custom(s) => s
  }
}

// 使用示例
let self_info = ComponentInfo::{
  name: "scheduler-core",
  component_type: NativeCore,  // 类型安全！
  status: Created,
  capabilities: ["scheduling", "component-mgmt", "message-dispatch"]
}
```

**为什么这样最好**：
- 类型安全，编译期检查
- 保留灵活性（Custom 变体）
- 易于理解和扩展

**⏳ 可作为后续改进项实施**

### 🔄 需要讨论：双层 ID 映射机制

#### temp.md 建议回顾：

> "外字符串，内整数"双层设计：
> - 对外（配置、日志）：字符串 ID（如 "app.camera"）
> - 对内（调度、消息）：整数 ID（如 2）

#### 我们的当前架构评估：

**当前状态**：
- ✅ 已经是整数 ID（0, 1, 2, 3...）
- ✅ name 字段是字符串（用于调试）
- ✅ components 使用 FixedArray，索引即 ID

**优点**：
- 性能极致（整数比较）
- 内存占用小
- 简单直接

**潜在问题**：
- 缺乏直观的树形结构表达
- ID 0, 1, 2... 语义不清晰

#### 🎯 最佳方案（平衡当前与未来）

**推荐方案：分层命名空间（非双层映射）**

我们不需要复杂的双层映射，而是采用：
1. **保持当前的高性能整数 ID**（0, 1, 2...）
2. **在配置和日志中使用字符串名称**（已经有 name 字段）
3. **添加能力层级前缀表达树形结构**

具体实现：

```moonbit
// 保持当前的高性能整数 ID 不变！
struct ComponentInfo {
  name: String  // 用 name 表达树形结构，如 "system.scheduler"
  component_type: ComponentType
  status: ComponentStatus
  capabilities: List[String]  // 能力也可以有层级
}

// 配置文件示例
components:
  - name: "system.scheduler"  # 字符串表达层级
    type: native-core
    capabilities: ["system.scheduling", "system.component-mgmt"]
  - name: "app.camera.ai"
    type: wasm
    capabilities: ["app.camera.detect"]

// 调度器内部：依然只使用整数 ID，极致性能！
fn dispatch(self: Scheduler, msg: @core.Message) -> Scheduler {
  let (to_id, _) = parse_to_id(msg)
  // 直接用整数比较，零开销！
  if to_id == 0 { /* 核心处理 */ }
  // ...
}

// 调试日志时：用 name 字段，人类可读
fn log_component_info(self: Scheduler, id: Int) {
  match self.components[id] {
    Some(comp) => println(comp.name)  // 打印 "system.scheduler"
    None => ()
  }
}
```

**✅ 结论：不需要双层映射，当前方案更好！**
