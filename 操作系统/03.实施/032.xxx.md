## 当前方案的问题

当前的架构有一条 "信息断层"：

```
bootstrap.yaml (系统文件，用户不可见)
     ↓ 内部硬编码引用
configs/components/counter.yaml (用户组件)
     ↓ 手工字符串解析 YAML → ComponentDescriptor
系统运行时
```

**断层在哪**：`load_component_descriptor` 的 if-else 是一种"系统内部预先知道有哪些组件"。如果换为从 `bootstrap.yaml` 的 `components:` 段读取 ref，那也是"系统指向用户"——还是系统的意志在主导。

而自举平台应该是：**系统只提供机制，不提供意志。造物主（用户）提供意志，系统执行。**

## 更符合"自举编程平台"的方案

### 1. 目录约定 取代 显式注册（最基础也最关键的改进）

```diff
- bootstrap.yaml 的 components: 段（系统告诉系统有哪些组件）
+ 系统扫描标准目录 convention:  components/*.yaml（文件系统告诉系统有哪些组件）
```

这是从 **push（系统推送组件列表）** 到 **pull（系统拉取发现的组件）** 的转变。用户创建一个 `.yaml` 文件放到 `components/`，系统就能发现它——不再需要任何地方"注册"。

这就和 Web 服务器的 `index.html` 一样：你把文件放进去，它就能被服务。这就是**约定优于配置**。

### 2. 组件自描述（携带自身元数据）

如果组件是 Wasm 模块，Wasm 组件模型本身就支持 metadata 和 WIT 嵌入。理想情况下：

```diff
- Component.yaml (外部描述)
+ Component.wasm 内部自带 WIT 描述，YAML 只是"给人类看的说明书"
```

但当前阶段保持 YAML 没问题，关键是 **YAML 和 wasm 二进制放在一起，系统通过目录发现它们**：

```
components/
  counter/
    Component.yaml    ← 人类可读的描述
    counter.wasm      ← 组件本身（自描述接口）
    wit/              ← WIT 接口定义（可选的详细定义）
```

这样 `Component.yaml` 可以不包含 `provides/requires`——直接从 wasm 二进制读取。YAML 只放人类需要的元数据（名称、版本、描述、实现选择策略）。

**但在 MVP 阶段，YAML 同时承担描述职责是合理的简化**，未来可以逐步把描述责任转移到 wasm 二进制自身。

### 3. 自举链条：系统的最小信任基

自举平台应该有一个清晰的 **信任基（Trusted Computing Base）** 和一个 **自举链**：

```
┌─ 信任基（必须硬编码）──────────────┐
│  "扫描 components/ 目录"           │  ← 这是唯一硬编码的约定
│  "解析 Component.yaml 格式"        │  ← 这是唯一硬编码的格式
│  "按依赖拓扑排序"                   │  ← 这是唯一硬编码的逻辑
└───────────────────────────────────┘
        ↓ 发现组件
┌─ 自举层（组件自己定义自己）──────────┐
│  components/scheduler/Component.yaml  │  ← 调度器也是一个普通组件
│  components/logger/Component.yaml     │  ← 日志也是一个普通组件
│  components/fs/Component.yaml         │  ← 文件系统也是一个普通组件
│  ...                                  │
└───────────────────────────────────┘
        ↓ 组件运行时
┌─ 应用层（用户定义）──────────────────┐
│  Application.yaml                    │  ← 造物主声明"我要什么"
│  components/user-app/Component.yaml  │  ← 用户自己的组件
└───────────────────────────────────┘
```

关键原则：**调度器、内存管理、甚至组件加载器本身，最终都应该用平台自身的组件机制来定义**。信任基只包含"怎么发现和解析组件"。

### 4. 可编程配置

你规范文档里已经写了 `if: "system.has_cuda == true"` 和 `${ Math.ceil(config.sample-rate * 0.02) }`，这就是"配置即编程"的方向。这意味着：

- YAML 不是静态数据，而是一种 **执行计划**
- 系统解析 YAML 时，实际上是在 **解释执行一段配置程序**
- 未来的配置可以用平台自身的语言（MoonBit/Wasm）来写，而不仅仅是 YAML

## 对你当前任务 #2 的建议

在这个 vision 下，任务 #2 的实现应该体现几个原则：

1. **移除硬编码**：删掉 `load_component_descriptor` 的 if-else，改为从 YAML 读取
2. **约定发现**：系统扫描 `components/` 目录（而不是靠 bootstrap.yaml 列举）
3. **格式就是协议**：`Component.yaml` 的格式就是平台的第一道契约，解析器必须完整支持规范中定义的 MVP 子集
4. **bootstrap.yaml 简化**：只保留系统级引导参数，去掉 `components:` 段
