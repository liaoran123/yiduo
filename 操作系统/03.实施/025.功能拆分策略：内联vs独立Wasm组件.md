# 功能拆分策略：内联vs独立Wasm组件

## 核心洞察：「管位置」 vs「管血液」

在讨论功能拆分之前，先明确一多 OS 与传统编排系统的本质差异：

| 维度 | Nomad / K8s (传统编排) | 一多 OS (可编程调度) |
|------|-----------------------|---------------------|
| **调度定位** | **管位置** - 集群资源分配器 | **管血液** - 应用级拓扑与生命周期管理者 |
| **调度粒度** | 粗粒度（Pod / Task / 容器级别） | 细粒度（Wasm 组件 / 接口调用级别） |
| **交互管理** | 不管（交由容器内的应用自行处理） | **强接管**（基于 WIT 契约自动路由、降级） |
| **通讯方式** | 依赖网络栈（HTTP/TCP）或系统 IPC | 零拷贝共享内存 + 链式数据自然流动 |

**因为一多 OS 要「管血液」，所以架构必须分层：**
- 🔴 **内联核心**：管血液流动的「血管系统」（消息路由、零拷贝、缓存）
- 🟢 **Wasm组件**：血液中流动的「细胞」（能力提供者、业务逻辑）

---

## 摘要

本文分析从成熟调度系统（Nomad、Kubernetes、WasmCloud）借鉴的功能，详细划分哪些应该内联在调度系统核心（性能关键），哪些可以拆分为独立Wasm组件（灵活可扩展）。

## 一、决策框架

### 1.1 拆分决策矩阵

| 维度 | 倾向内联 | 倾向Wasm组件 |
|-----|---------|------------|
| **性能要求** | 热路径、<1ms延迟 | 后台处理、>10ms延迟 |
| **调用频率** | 每请求百万次 | 每分钟几次或更少 |
| **变更频率** | 核心逻辑稳定 | 业务规则频繁变化 |
| **安全隔离** | 可信核心 | 第三方插件 |
| **复杂度** | 简单且关键 | 复杂但独立 |
| **定制化需求** | 标准统一 | 各场景不同 |

### 1.2 决策流程图

```
新功能需求
     │
     ├─ 性能关键？
     │   ├─ 是 ──┐
     │   │       ├─ 调用频率高？
     │   │       │   ├─ 是 ──> ✅ 内联到调度核心
     │   │       │   └─ 否 ──> ⚖️ 看复杂度
     │   │       │
     │   └─ 否 ──> ✅ Wasm组件
     │
     ├─ 需要动态更新？
     │   ├─ 是 ──> ✅ Wasm组件
     │   └─ 否 ──> ⚖️ 看其他因素
     │
     ├─ 第三方可定制？
     │   ├─ 是 ──> ✅ Wasm组件
     │   └─ 否 ──> ⚖️ 看其他因素
     │
     └─ 安全隔离要求？
         ├─ 是 ──> ✅ Wasm组件
         └─ 否 ──> ⚖️ 看其他因素
```

## 二、HashiCorp Nomad 功能拆分

### 2.1 Nomad核心功能分析

| Nomad功能 | 是否性能关键 | 建议方案 | 理由 |
|---------|-----------|---------|-----|
| **调度算法核心** | ✅ 极高 | 内联 | 每次调度都要运行，纳秒级优化 |
| **Bin-Packing装箱** | ✅ 极高 | 内联 | 核心调度逻辑 |
| **反亲和规则** | ✅ 高 | 内联 | 调度决策的一部分 |
| **任务驱动接口** | ⚖️ 中 | Wasm组件 | 可插拔的驱动，不同场景需要不同驱动 |
| **健康检查探针** | ⚖️ 中 | 混合架构 | 框架内联，具体探针Wasm |
| **服务发现集成** | ❌ 低 | Wasm组件 | Consul、Etcd等多种实现 |
| **密钥管理集成** | ❌ 低 | Wasm组件 | Vault、KMS等多种实现 |
| **CLI命令处理** | ❌ 低 | Wasm组件 | 易变的用户界面 |

### 2.2 Nomad功能详细建议

#### 🔴 必须内联的核心功能

```rust
// ========== 内联到调度核心 ==========
pub struct SchedulerCore {
    // 1. 核心调度算法
    bin_packer: BinPacker,
    anti_affinity: AntiAffinityEngine,
    
    // 2. 节点筛选（关键路径）
    node_evaluator: NodeEvaluator,
    
    // 3. 资源管理（热路径）
    resource_accountant: ResourceAccountant,
    
    // 4. 状态存储（性能关键）
    state_store: StateStore,
}

// 这些功能每次调度决策都要运行，不能有Wasm开销
impl SchedulerCore {
    #[inline(always)]  // 强制内联，零开销
    pub fn schedule(&self, job: &Job) -> SchedulingDecision {
        // 纳秒级的关键路径
        let candidates = self.filter_nodes(job);
        let best_node = self.bin_packer.pack(candidates, job);
        SchedulingDecision { node: best_node }
    }
}
```

### 3.2 Kubernetes功能详细建议

#### 🔴 必须内联的核心功能

```rust
// ========== 内联到调度核心 ==========
pub struct KubeSchedulerCore {
    // 1. 调度框架核心
    scheduling_framework: SchedulingFramework,
    
    // 2. 节点打分（关键路径）
    score_plugins: Vec<Box<dyn ScorePlugin>>,  // 关键插件内联
    
    // 3. 缓存层
    cache: SchedulerCache,
    
    // 4. API Server核心
    api_handler: ApiHandler,
}

// 性能关键的调度插件应该内联
impl SchedulingFramework {
    #[inline]
    pub fn filter(&self, pod: &Pod, nodes: &[Node]) -> Vec<Node> {
        // 关键的过滤逻辑内联
        let mut filtered = Vec::new();
        for node in nodes {
            if self.pod_fits_resources(pod, node)
                && self.pod_tolerates_taints(pod, node)
                && self.pod_matches_node_selector(pod, node)
            {
                filtered.push(node.clone());
            }
        }
        filtered
    }
}
```

## 四、WasmCloud/Spin 功能拆分

### 4.2 WasmCloud功能详细建议

#### 🔴 必须内联的核心功能

```rust
// ========== 内联到调度核心 ==========
pub struct WasmCloudRuntimeCore {
    // 1. Wasm执行引擎
    wasm_engine: WasmtimeEngine,
    
    // 2. 消息路由（热路径）
    message_router: MessageRouter,
    
    // 3. 本地调用优化
    local_dispatch: LocalDispatcher,
    
    // 4. 内存管理
    memory_manager: MemoryManager,
}

// 消息派发是最关键的路径，必须内联
impl MessageRouter {
    #[inline(always)]
    pub fn dispatch(&self, from: ActorId, to: ActorId, msg: &Message) -> Result<(), Error> {
        // 检查是否本地Actor
        if let Some(local) = self.local_actors.get(&to) {
            // 零拷贝本地调用
            return local.call(msg);
        }
        
        // 远程调用走网络
        self.remote_dispatch(from, to, msg)
    }
}
```

## 六、性能优化技巧：让Wasm组件也很快

### 6.1 关键优化技术

即使是Wasm组件，也可以通过以下技术接近Native性能：

| 优化技术 | 效果 |
|---------|-----|
| **AOT提前编译** | Wasm → 机器码，~10ns调用 |
| **内存共享** | 零拷贝数据传输 |
| **L1缓存热组件** | 常用组件直接函数指针调用 |
| **批处理** | 多次调用合并处理 |

### 6.2 性能分层模型

```
性能金字塔（从快到慢）：
┌───────────────────────────────────────────┐
│ 🔴 内联函数调用           ~0.1-1ns        │
├───────────────────────────────────────────┤
│ 🟡 Native AOT Wasm       ~10-50ns        │
├───────────────────────────────────────────┤
│ 🟢 Wasm JIT (Wasmtime)   ~100-500ns      │
├───────────────────────────────────────────┤
│ 🟢 本地Wasm (非AOT)      ~1-5μs          │
├───────────────────────────────────────────┤
│ 🟢 远程调用              ~50-500μs        │
└───────────────────────────────────────────┘
```

### 6.3 自适应调度策略

```rust
// 根据性能需求自动选择组件实现
pub struct AdaptiveScheduler {
    components: HashMap<ComponentId, ComponentImplementation>,
}

impl AdaptiveScheduler {
    pub fn select_implementation(
        &self,
        requirement: &ComponentRequirement,
        latency_budget: Duration,
    ) -> &ComponentImplementation {
        // 1. 如果延迟预算<1μs，强制Native实现
        if latency_budget < Duration::from_micros(1) {
            return self.find_native_implementation(requirement);
        }
        
        // 2. 如果延迟预算<100μs，优先AOT Wasm
        if latency_budget < Duration::from_micros(100) {
            if let Some(aot) = self.find_aot_wasm_implementation(requirement) {
                return aot;
            }
        }
        
        // 3. 否则用标准Wasm
        self.find_standard_wasm_implementation(requirement)
    }
}
```

## 七、总结与最佳实践

### 7.1 核心原则总结

| 原则 | 说明 |
|-----|-----|
| **1. 关键路径全内联** | 调度决策、消息路由、缓存访问必须内联 |
| **2. 业务逻辑全组件** | 能力提供者、探针、集成全部Wasm化 |
| **3. 混合架构灵活** | 框架内联，策略/实现Wasm，兼得性能与灵活性 |
| **4. 性能分层** | 根据延迟预算自动选择实现 |
| **5. 优先优化热路径** | 99%的时间花在1%的代码上，优化那1% |

### 7.2 一多OS相对于其他系统的优势

| 系统 | 架构 | 优势 | 劣势 |
|-----|------|-----|-----|
| **Kubernetes** | 单体 + 插件 | 生态丰富 | 核心重，插件扩展性有限 |
| **Nomad** | 单体 + Task Driver | 简单高效 | 插件机制较简单 |
| **WasmCloud** | 全Wasm组件化 | 极其灵活 | 全部Wasm，部分场景性能不够 |
| **一多OS** | 🔴内联核心+🟢Wasm组件 | **既快又灵活！** | 需要仔细设计拆分边界 |

### 7.3 最终架构价值

一多OS的混合架构带来：
- ✅ **极致性能**：关键路径内联，纳秒级优化
- ✅ **完全灵活**：所有业务逻辑Wasm组件化
- ✅ **安全隔离**：Wasm沙箱隔离第三方代码
- ✅ **易于演进**：组件可独立升级，不影响核心
- ✅ **生态友好**：清晰的组件接口，易于贡献

这就是一多OS的核心优势：**不做二选一的选择题，而是两者兼得的最优解！** 🚀
