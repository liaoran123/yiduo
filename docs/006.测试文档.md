# 一多 OS 测试文档

## 概述

一多 OS 的测试体系覆盖**调度器核心**（7个白盒测试）、**全链路集成**（5个集成测试）和**双模运行时**（11个白盒测试），共计 **27 个测试用例，全部通过**。此外还有一个**基准测试**用于性能基线评估。

测试验证的核心架构关系：

```
┌──────────────────────────────────────────────────────┐
│                   测试覆盖全景                         │
├──────────────────────────────────────────────────────┤
│  配置层        调度层          内存层       验证层    │
│  (YAML解析) → (优先级/亲和度) → (句柄安全) → (断言)   │
│     │              │              │             │     │
│     ▼              ▼              ▼             ▼     │
│  parse_bootstrap  Scheduler   MemoryManager  assert_eq │
│  _yaml()         .process_   .transfer_     .to_      │
│                   one()       ownership()   string()   │
└──────────────────────────────────────────────────────┘
```

## 测试文件结构

```
runtime/
├── scheduler/
│   ├── scheduler_wbtest.mbt      ← 调度器白盒测试（7个）
│   └── dual_runtime_wbtest.mbt   ← 双模运行时测试（11个）

└── benchmark/
    └── basic_benchmark.mbt       ← 性能基准测试（基准数据）
```

### 运行方式

```bash
# 运行所有测试
moon test

# 仅构建（不运行测试）
moon build

# 运行基准测试
moon run runtime/benchmark

# 格式化代码并更新接口
moon fmt && moon info
```

## 一、调度器白盒测试

**文件**：[scheduler_wbtest.mbt](file:///d:/yiduo/runtime/scheduler/scheduler_wbtest.mbt)
**数量**：7 个
**类型**：白盒测试（可访问调度器内部状态如队列长度、亲和度表）

### 测试 1：基础消息流 (e2e_basic_message_flow)

| 项目 | 内容 |
|------|------|
| **目的** | 验证消息从发送到入队再到分发的完整路径 |
| **场景** | 组件 A (comp-a) → 发消息 → 组件 B (comp-b) |
| **调度器配置** | `Scheduler::create()` 默认配置 |

步骤：
1. 创建调度器
2. 注册组件 comp-a（ID:0）和 comp-b（ID:1）
3. comp-a 向 comp-b 发送高优先级消息
4. 断言：发送成功（`ok == true`），高优队列长度为 1
5. 执行 `process_one()` 处理消息
6. 断言：处理后高优队列为空

### 测试 2：优先级顺序 (e2e_priority_ordering)

| 项目 | 内容 |
|------|------|
| **目的** | 验证高优先 > 普通 > 低优的调度顺序 |
| **场景** | 依次发送低→普通→高三条消息，只处理一条 |

步骤：
1. 创建调度器，注册目标组件
2. 依次发送低优、普通、高优消息（发送顺序与优先级顺序反向）
3. 断言：三个队列各有一条消息
4. 执行 `process_one()` 一次
5. 断言：高优队列已处理，普通和低优队列保持不变

### 测试 3：组件亲和度追踪 (e2e_affinity_tracking)

| 项目 | 内容 |
|------|------|
| **目的** | 验证调度器根据通信频率追踪组件间亲和度 |
| **场景** | A→B 通信 10次，A→C 通信 2次，查询 A 的最高亲和度 |

步骤：
1. 创建带内存管理器的调度器（`create_with_config`）
2. 注册组件 A、B、C
3. A→B 发送 10 条消息
4. A→C 发送 2 条消息
5. 查询 A 的亲和度最高的组件
6. 断言：最高亲和度为 B

### 测试 4：句柄安全 (e2e_handle_safety)

| 项目 | 内容 |
|------|------|
| **目的** | 验证所有权转移后的越权释放防护和双重释放防护 |
| **场景** | A 分配句柄 → 转移给 B → A 尝试释放（应拒绝）→ B 释放（应成功）→ B 二次释放（应拒绝） |

步骤：
1. 创建内存池和内存管理器
2. 注册组件 A 和 B
3. A 分配 128 字节句柄
4. 转移所有权给 B
5. 断言：A 释放被拒绝（`free_a_ok == false`）
6. 断言：B 释放成功（`free_b_ok == true`）
7. 断言：B 二次释放被拒绝（`double_free_ok == false`）

### 测试 5：句柄完整生命周期 (e2e_handle_full_lifecycle)

| 项目 | 内容 |
|------|------|
| **目的** | 验证句柄分配→转移→释放→无效标记的完整路径 |
| **场景** | A 分配句柄 → 转移给系统(0) → 系统释放 → 验证句柄 `is_valid == false` |

步骤：
1. 创建内存池和内存管理器
2. 注册组件 A
3. A 分配 256 字节句柄
4. 转移所有权给 ID:0
5. ID:0 释放句柄
6. 断言：句柄信息中 `is_valid == false`

### 测试 6：批处理功能 (e2e_batch_processing)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 `batch_size` 机制一次性处理多条消息 |
| **调度器** | `batch_size = 4` |

步骤：
1. 创建调度器（batch_size=4）
2. 注册目标组件
3. 发送 4 条普通消息
4. 断言：普通队列长度为 4
5. 执行 `process_batch()`
6. 断言：处理后队列为空

### 测试 7：运行循环 (e2e_run_loop)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 `run_loop` 连续处理所有消息 |
| **调度器** | `batch_size = 2` |

步骤：
1. 创建调度器（batch_size=2）
2. 注册目标组件
3. 发送 10 条普通消息
4. 断言：队列长度为 10
5. 执行 `run_loop(5)`（5轮批处理，每轮最多2条）
6. 断言：队列为空

## 二、双模运行时白盒测试

**文件**：[dual_runtime_wbtest.mbt](file:///d:/yiduo/runtime/scheduler/dual_runtime_wbtest.mbt)
**数量**：7 个
**类型**：白盒测试（可访问 HandlerRegistry 内部状态）

### 测试 1：处理器注册与调用 (dual_native_handler_registration)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 HandlerRegistry 能正确注册和调用 Native 处理器 |
| **场景** | 注册处理器 → 调用 → 验证调用计数 → 越界 ID 调用返回 false |

步骤：
1. 创建 HandlerRegistry（max=32）
2. 注册处理器到 ID 5
3. 调用处理器（断言：返回 true，调用计数=1）
4. 调用越界 ID 99（断言：返回 false）

### 测试 2：Native 组件调度 (dual_native_scheduler_handler)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 Native 组件通过 Scheduler 注册处理器并调度的完整链路 |
| **场景** | 注册组件(ID:1) → 注册处理器 → 直接调用(1次) → 发送消息(1条) → process_one() 触发调度 |

步骤：
1. 创建调度器，注册 Native 组件（ID:1，保留 ID:0 给调度核心）
2. 注册处理器，直接调用验证（计数+1）
3. 通过 send_small 发送消息
4. 断言：处理器仍存在
5. process_one() 处理消息
6. 断言：处理器被调度调用（计数=2），队列为空

### 测试 3：Wasm 组件调度 (dual_wasm_component_scheduling)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 Wasm 组件调度路径不会崩溃（预留接口） |
| **场景** | 注册 Wasm 组件 → 发送消息 → process_one() 不应崩溃 |

步骤：
1. 创建调度器，注册 Wasm 组件
2. 断言：无预注册的 Native 处理器
3. 发送消息到 Wasm 组件
4. process_one() 处理（断言：不崩溃）

### 测试 4：混合调度 (dual_hybrid_scheduling)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 Native + Wasm 组件共存时的混合调度 |
| **场景** | 注册 Native(ID:1) + Wasm(ID:2) → 注册 Native 处理器 → 发送消息到两者 → 顺序处理 |

步骤：
1. 创建调度器
2. 注册 Native 组件（ID:1）和 Wasm 组件（ID:2）
3. 注册 Native 处理器
4. Native 消息入高优队列，Wasm 消息入普通队列
5. 处理 Native 消息（断言：处理器被调用，队列清空）
6. 处理 Wasm 消息（断言：不崩溃，队列清空）

### 测试 5：组件类型枚举正确性 (dual_component_type_enum)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 ComponentType 枚举的 to_string 和相等比较 |
| **场景** | Native/Wasm/MoonBit 类型的字符串和相等断言 |

步骤：
1. 创建三种类型的 ComponentType
2. 断言：to_string 返回正确值（"native"/"wasm"/"moonbit"）
3. 断言：相等比较（同类型相等，不同类型不等）

### 测试 6：处理器注册表边界条件 (dual_handler_registry_boundary)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 HandlerRegistry 的边界条件处理 |
| **场景** | 负数 ID 注册/调用 → 越界 ID 注册/调用 → 注册 → 解注册 → 验证状态 |

步骤：
1. 创建 HandlerRegistry（max=16）
2. 注册负数 ID（断言：无影响）
3. 注册越界 ID（断言：无影响）
4. 调用负数 ID（断言：返回 false）
5. 调用越界 ID（断言：返回 false）
6. 注册 → 调用（断言：返回 true）
7. 解注册 → 调用（断言：返回 false）

### 测试 7：Native 多消息处理 (dual_native_multiple_messages)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 Native 组件能连续处理多条消息 |
| **场景** | 发送 5 条消息到 Native 组件 → process_batch() 批量处理 → 全部处理 |

步骤：
1. 创建调度器，注册 Native 组件
2. 注册处理器
3. 循环发送 5 条消息（每条断言成功）
4. 断言：高优队列有 5 条消息
5. 执行 process_batch() 批量处理
6. 断言：全部 5 条消息处理器被调用，队列为空

### 测试 8：Wasm 计数器组件 (real_wasm_counter_component)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 Wasm 模拟运行时的计数器组件功能 |
| **场景** | 注册 Wasm 计数器 → 发送 2 条消息 → 逐条处理 → 验证计数 |

步骤：
1. 创建调度器，注册 Wasm 类型组件
2. 通过 register_wasm_handler 注册计数器处理器
3. 发送 2 条消息到 Wasm 组件
4. 处理第 1 条消息（断言：计数=1）
5. 处理第 2 条消息（断言：计数=2）
6. 断言：高优队列清空

### 测试 9：Wasm 累加器组件 (real_wasm_accumulator_component)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 Wasm 模拟运行时的累加器组件功能 |
| **场景** | 注册 Wasm 累加器 → 发送 3 条不同值消息 → 批处理 → 验证总和 |

步骤：
1. 创建调度器，注册 Wasm 类型组件
2. 通过 register_wasm_handler 注册累加器处理器
3. 发送 msg_type=10/20/30 共 3 条消息到 Wasm 组件
4. 执行 process_batch() 批量处理
5. 断言：累加总和 = 60，普通队列清空

### 测试 10：多 Wasm 组件独立状态 (real_wasm_multiple_components)

| 项目 | 内容 |
|------|------|
| **目的** | 验证多个 Wasm 组件有独立的模拟状态 |
| **场景** | 注册 wasm-1/wasm-2 → 不同处理器 → 发 3 条消息 → 验证独立 |

步骤：
1. 创建调度器，注册 2 个 Wasm 组件
2. wasm-1 处理器：count1+=1，wasm-2 处理器：count2+=2
3. 发送 2 条消息到 wasm-1，1 条消息到 wasm-2
4. 执行 process_batch() 批量处理
5. 断言：count1=2（2条），count2=2（1条 ×2）

### 测试 11：Native + Wasm 分立处理 (real_wasm_native_hybrid)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 Native 和 Wasm 组件通过不同 handler 注册表独立处理 |
| **场景** | Native(ID:1) + Wasm(ID:2) → 各注册处理器 → 优先级调度 |

步骤：
1. 创建调度器，注册 Native + Wasm 各 1 个
2. Native 使用 register_handler，Wasm 使用 register_wasm_handler
3. Native 发 2 条高优消息，Wasm 发 3 条普通消息
4. 逐条处理高优消息（断言：Native 累加=5→15，Wasm=0）
5. 批处理普通消息（断言：Wasm 累加=5+10+5=20）

## 三、全链路集成测试

**文件**：[integration_wbtest.mbt](file:///d:/yiduo/runtime/integration_wbtest.mbt)
**数量**：5 个
**类型**：白盒集成测试（跨 config + scheduler + core 三个包）

### 测试数据：模拟 bootstrap.yaml

测试用嵌入的 YAML 文本（与真实 [bootstrap.yaml](file:///d:/yiduo/configs/bootstrap.yaml) 结构一致）：

```yaml
system:
  name: Yiduo OS MVP
  version: 0.1.0
  description: 一多操作系统最小启动器
chain:
  foundation:
    - base/types
    - base/error
  core:
    - env/component
    - config/loader
  extensions:
    - env/fs
components:
  - name: wasm-runtime
    type: native
    provides:
      - wasm-executor
    required: true
  - name: config-parser
    type: native
    provides:
      - config-loader
    required: true
bootstrap:
  mode: minimal
  log-level: info
  first-component: wasm-runtime
```

### 测试 1：解析真实配置文件 (integration_parse_real_config)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 `parse_bootstrap_yaml()` 能正确解析完整 YAML 配置 |
| **涉及模块** | config（parse_bootstrap_yaml, config_types） |

步骤：
1. 调用 `parse_bootstrap_yaml(BOOTSTRAP_YAML)`
2. 断言：
   - `system.name == "Yiduo OS MVP"`
   - `system.version == "0.1.0"`
   - `bootstrap.mode.to_string() == "minimal"`
   - `bootstrap.log_level.to_string() == "info"`
   - `bootstrap.first_component == "wasm-runtime"`

### 测试 2：完整 bootstrap 流程 (integration_full_bootstrap_flow)

| 项目 | 内容 |
|------|------|
| **目的** | 验证内存初始化→调度器创建→组件注册→跨组件消息→run_loop 处理完整链路 |
| **涉及模块** | core (MemoryManager, MemoryPool) + scheduler (Scheduler) |

步骤：
1. 创建 `MemoryPool`（4096 字节块，64 块）和 `MemoryManager`
2. 创建 `Scheduler`（batch_size=8, max_components=32），关闭调试日志
3. 注册 scheduler-core（`running`）、wasm-runtime（`created`）、config-parser（`created`）
4. wasm-runtime → config-parser 发送高优消息（断言成功）
5. config-parser → scheduler-core 发送普通消息（断言成功）
6. 执行 `run_loop(5)` 处理所有消息
7. 处理后再次发送低优消息并处理（断言成功）

验证的完整链路：
```
MemoryPool → MemoryManager → Scheduler → register → send_small → run_loop → process_one
```

### 测试 3：多组件多优先级消息流 (integration_multi_component_flow)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 4 个组件 + 3 种优先级的混合消息处理 |
| **组件** | gateway, auth, processor, storage |
| **消息链** | gateway→auth(高优) → gateway→processor(普通) → processor→storage(低优) |

步骤：
1. 创建调度器（batch_size=4, max_components=32）
2. 注册 4 个组件（gateway, auth, processor, storage）
3. gateway→auth 发送高优消息
4. gateway→processor 发送普通消息（断言成功）
5. processor→storage 发送低优消息
6. 执行 3 次 `process_one()` 处理所有消息
7. 处理后 gateway→auth 再次发送高优消息（断言成功）

### 测试 4：句柄安全全生命周期 (integration_handle_safe_lifecycle)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 `MemoryManager` 的分配→转移→释放→二次释放防护完整路径 |
| **涉及模块** | core (MemoryPool, MemoryManager) |

步骤：
1. 创建 `MemoryPool` 和 `MemoryManager`
2. 组件 1 分配 256 字节句柄（断言成功）
3. 转移所有权给组件 2（断言成功）
4. 组件 1 尝试释放（断言：拒绝）
5. 组件 2 释放（断言：成功）
6. 组件 2 二次释放（断言：拒绝）

### 测试 5：高吞吐消息处理 (integration_high_throughput_messaging)

| 项目 | 内容 |
|------|------|
| **目的** | 验证 20 条消息批量发送 + 10 轮 run_loop 的高吞吐处理 |
| **调度器** | batch_size=8, max_components=32 |

步骤：
1. 创建调度器，注册 worker 组件
2. 循环发送 20 条普通消息，每条断言发送成功
3. 执行 `run_loop(10)` 处理所有消息
4. 处理后再次发送高优消息（断言成功）

## 五、调试日志说明

调度器支持 `debug_log` 开关控制调试输出：

```moonbit
// 开启调试日志（默认）
let s = Scheduler::create()

// 关闭调试日志（基准测试/生产环境）
let s = Scheduler::set_debug_log(s, false)
```

测试中通过 `set_debug_log(s, false)` 关闭日志输出，避免日志干扰测试结果的准确性。基准测试同样关闭了调试日志。

## 六、测试设计原则

1. **确定性**：所有测试使用固定的种子数据，无随机因素
2. **自治性**：每个测试独立创建自己的调度器和内存管理器
3. **可重复性**：测试可反复运行，结果始终一致
4. **层次化**：从单元级（调度器白盒）到集成级（config→scheduler→core）
5. **边界覆盖**：句柄安全的错误路径（越权、双重释放）有专门的负面测试
