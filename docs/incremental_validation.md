# 增量验证设计文档

## 核心思想

**只重新验证变更的文件！**

## 方案说明

### 最简单的实现方案

不需要复杂的依赖分析，只需要：

1. **缓存验证结果**
   - 记录每个文件的验证结果
   - 记录文件的修改时间

2. **检查是否需要重新验证**
   ```
   当验证文件时:
     if (文件当前修改时间 > 缓存记录的修改时间):
         重新验证
         更新缓存
     else:
         直接用缓存结果
   ```

### 数据结构

```
缓存条目: {
  文件路径: String
  文件修改时间: Int64  // 时间戳
  验证结果: Bool
  验证时间: Int64
}

验证器: {
  缓存: Map<文件名 -> 缓存条目>
}
```

### 工作流程

```
第一轮验证:
  [验证] audio.yaml  ← 第一次验证
  [验证] camera.yaml ← 第一次验证

第二轮验证 (相同文件):
  [缓存命中] audio.yaml  ← 没变，用缓存
  [缓存命中] camera.yaml ← 没变，用缓存

第三轮验证 (audio.yaml 变更):
  [验证] audio.yaml  ← 变了，重新验证
  [缓存命中] camera.yaml ← 没变，用缓存
```

## 性能优势

| 场景 | 全量验证 | 增量验证 | 提升 |
|------|---------|---------|------|
| 单文件变更 (1000 组件) | 1000 次 | 1 次 | 1000x ⚡ |
| 小部分变更 (1%) | 1000 次 | 10 次 | 100x |
| 大规模变更 (50%) | 1000 次 | 500 次 | 2x |

## 为什么这个方案足够好？

1. **简单**：文件系统已经提供了修改时间
2. **有效**：解决 99% 的性能问题
3. **不需要复杂依赖分析**：不需要追踪组件间的依赖关系

## 与四元架构的关系

| 四元架构 | 验证系统对应 |
|---------|------------|
| 💭 配置文件 = 意志 | 验证的输入 |
| 🧬 器官 = DNA | 验证的对象 |
| 🌳 树形 = 生长路径 | (高级功能，暂不需要) |
| 🩸 链式 = 血液系统 | 接口验证 (单独实现) |

## 下一步

当系统更复杂时，可以考虑：
- 增加依赖追踪
- 增量验证依赖链
- 持久化缓存到磁盘

但现在，这个简单方案就足够好了！
